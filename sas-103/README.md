## 1. Введение: роль и задачи системного аналитика

### 1.1. Три измерения работы аналитика

Деятельность системного аналитика описывается через три взаимосвязанных понятия, которые вместе образуют полный цикл профессиональной работы.

| Измерение     | Что это                                                                                        | Пример                                         |
|---------------|------------------------------------------------------------------------------------------------|------------------------------------------------|
| **Задача**    | Мыслительные операции и процессы: выявление потребностей, анализ, структурирование информации  | Выявить сценарии использования                 |
| **Артефакт**  | Осязаемые результаты: документы, схемы, модели, спецификации — всё, что можно передать команде | Use Case диаграмма                             |
| **Результат** | Ценность для команды: улучшение качества, скорости и взаимопонимания внутри команды и продукта | Разработчик точно знает, что именно кодировать |

**Цепочка:** Задача → Артефакт → Результат. Убрать любое звено — и ценность работы аналитика становится невидимой для команды.

### 1.2. Ключевые задачи системного аналитика

1. **Исследование и выявление потребностей** — умение услышать истинную проблему за запросом стейкхолдера.
2. **Формализация требований** — перевод с бизнесового языка на технический: точный, однозначный, проверяемый.
3. **Декомпозиция** — разбить крупную задачу на атомарные, связанные между собой части, удобные для реализации.
4. **Валидация** — убедиться, что требования корректны, полны, непротиворечивы и технически реализуемы.

### 1.3. Hard skills и soft skills

| Hard Skills                                            | Soft Skills                                                               |
|--------------------------------------------------------|---------------------------------------------------------------------------|
| SQL — работа с данными и проверка гипотез              | Системное мышление — видеть целое, не теряя деталей                       |
| UML / BPMN — моделирование процессов и поведения       | Критическое мышление — задавать правильные вопросы                        |
| OpenAPI / Swagger — описание интеграционных контрактов | Структурирование — превращать хаос в ясность                              |
| Draw.io, Figma — создание схем и прототипов            | Эмпатия — понимать боли стейкхолдеров                                     |
| Postman — тестирование и валидация API                 | Умение договариваться — находить компромисс между бизнесом и технологиями |

> **Без hard skills — нет артефактов. Без soft skills — непонятно, какие артефакты нужны.**

### 1.4. Шесть ключевых артефактов аналитика

1. **Vision & Scope** — видение и границы проекта.
2. **Реестр требований** — функциональные и нефункциональные требования.
3. **Модель данных** — ERD, словарь данных.
4. **API-контракты** — OpenAPI/Swagger спецификации.
5. **Динамические схемы** — Sequence, BPMN, Activity.
6. **SRS** — Software Requirements Specification.

### 1.5. Невидимые, но важные результаты

Часть ценности работы аналитика не материализуется в документах — она живёт в головах людей и культуре команды:

- **Общий контекст команды** — Shared Understanding: каждый участник понимает, зачем мы это строим, какую проблему решаем и для кого.
- **Снижение неопределённости** — чем меньше додумываний на старте, тем меньше дорогостоящих переделок на поздних этапах разработки.
- **Трассируемость решений** — всегда можно вернуться и ответить на вопрос: «Почему мы сделали именно так?».

### 1.6. Роли и границы ответственности

| Роль                                | Отвечает за                                                                                                                          | Не отвечает за                                                     |
|-------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------|
| Бизнес-стейкхолдер                  | Бизнес-цели, приоритеты, приёмку                                                                                                     | Техническую реализуемость, структуры данных                        |
| Бизнес-аналитик / владелец продукта | Формулировку требований бизнес-уровня, ценность                                                                                      | Техническую декомпозицию, моделирование данных                     |
| **Системный аналитик**              | Декомпозицию на требования, сценарии, правила, сущности, состояния, интеграции; трассировку; верификацию; выявление неоднозначностей | Бизнес-приоритеты, архитектурные решения вне домена, реализацию БД |
| Архитектор                          | Физическую архитектуру, выбор технологий                                                                                             | Содержание требований, бизнес-правила                              |
| Разработчик                         | Реализацию                                                                                                                           | Интерпретацию требований без подтверждения аналитика               |
| QA                                  | Проектирование тестов, проверяемость                                                                                                 | Владение требованиями                                              |

Если решение принадлежит другой роли — оно выносится как **открытый вопрос**, а не принимается молча.

## 2. Жизненный цикл разработки (SDLC)

### 2.1. Этапы жизненного цикла

SDLC (Software Development Life Cycle) — жизненный цикл разработки программного обеспечения. Включает:

1. **Инициация** — анализ осуществимости, оценка трудозатрат и сроков, определение границ системы.
2. **Сбор и анализ требований** — уточняющие вопросы, интервью, работа с документами.
3. **Проектирование** — детализация шагов, системные реакции, сценарии, интеграции.
4. **Разработка** — сценарий как основа для написания кода, реализуются все потоки.
5. **Тестирование** — тест-кейсы на основе всех трёх типов сценариев.
6. **Внедрение** — приёмочное тестирование (UAT), обучение, документация.
7. **Сопровождение** — сбор обратной связи, анализ использования, реестр проблем и пожеланий.

### 2.2. Роль аналитика на этапах SDLC

**На этапе инициации:**
- Анализ осуществимости — можно ли реализовать идею технически и экономически.
- Оценка трудозатрат и сроков — сколько это будет стоить и сколько времени займёт разработка.
- Определение границ системы — что мы строим, а что сознательно оставляем за рамками.

**Перед внедрением:**
- Готовит приёмочные критерии и тестовые сценарии на основе описанных пользовательских сценариев (но не фактический план тестирования и тест-кейсы — это работа тестировщика).
- Участвует в приёмочном тестировании (UAT) вместе с заказчиком.
- Готовит пользовательскую документацию и инструкции.
- Помогает организовать обучение сотрудников заказчика, если это требуется.

**После внедрения:**
- Собирает обратную связь от реальных пользователей.
- Анализирует, как система используется на практике и где реальное поведение отличается от предполагаемых сценариев.
- Ведёт реестр обнаруженных проблем и пожеланий по доработке.
- Помогает с разбором спорных случаев работы системы.

### 2.3. Методологии разработки

| Методология                      | Описание                                                                                                                                                     |
|----------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Waterfall (каскадная модель)** | Последовательные этапы (анализ → дизайн → разработка → тестирование → внедрение), каждый завершается перед следующим, требования почти не меняются по ходу.  |
| **Agile**                        | Не методология, а философия: короткие циклы, постоянная обратная связь, готовность менять требования даже на поздних этапах.                                 |
| **Scrum**                        | Работа фиксированными спринтами (1–4 недели), с ролями (Product Owner, Scrum Master, команда) и регулярными церемониями (планирование, дейли, ревью, ретро). |
| **Kanban**                       | Непрерывный поток задач без спринтов, доска с колонками и WIP-лимитами на количество задач в работе одновременно.                                            |

### 2.4. Три уровня описания интерфейса

| Уровень            | Что описывает                                       | Кто работает                       |
|--------------------|-----------------------------------------------------|------------------------------------|
| **Концептуальный** | Зачем нужна фича, задача пользователя               | Бизнес-аналитик и UX-исследователь |
| **Логический**     | Что и как функционирует, элементы, связи, поведение | Системный аналитик                 |
| **Визуальный**     | Как выглядит — цвета, шрифты, макет                 | Дизайнер                           |

Логический уровень — мост между потребностью пользователя и готовым макетом.

## 3. Сбор информации: интервью, анализ материалов, фиксация вводных

### 3.1. Зачем аналитику навык проведения интервью

Интервью — основной инструмент сбора первичной информации. Плохо проведённое интервью даёт искажённые требования, которые ведут к неверным решениям и потере времени всей команды. Навык интервьюирования можно развить — это не талант, а технология с конкретными инструментами и приёмами.

### 3.2. Полный цикл работы с интервью

Каждый этап цикла влияет на качество итогового результата:

1. **Подготовка** — вопросы, гипотезы, изучение контекста и роли собеседника.
2. **Проведение** — открытие, основная часть, закрытие и устное резюме.
3. **Фиксация** — протокол встречи и подтверждение договорённостей.
4. **Анализ** — уточнения, нестыковки и новые гипотезы для проверки.

### 3.3. Подготовка к интервью

Аналитик, который приходит на интервью неподготовленным, тратит половину времени на то, чтобы понять базовые вещи. Это раздражает респондента и снижает качество разговора.

**Что нужно сделать до встречи:**
- **Изучить доступные материалы** — документы, регламенты, переписка, существующие процессы.
- **Понять роль собеседника** — зачем этот человек участвует в процессе, какова его мотивация, что для него важно.
- **Использовать ИИ-инструменты** — быстро входить в незнакомую предметную область: получать глоссарий, типовые процессы, ключевые термины отрасли.

**Результат подготовки:** вы заходите на интервью не с чистого листа, а с базовым пониманием. Это позволяет сразу задавать умные, точные вопросы.

### 3.4. Типы вопросов

| Тип вопроса          | Назначение                         | Пример                                                        |
|----------------------|------------------------------------|---------------------------------------------------------------|
| **Открытые**         | Запускают рассказ и дают контекст  | «Опишите ваш типичный рабочий день»                           |
| **Закрытые**         | Уточняют конкретные детали и цифры | «Сколько заявок вы обрабатываете в день?»                     |
| **Вопросы-триггеры** | Вскрывают реальные боли            | «Что вас больше всего раздражает в текущей системе?»          |
| **Сценарные**        | Моделируют желаемое будущее        | «Представьте, что система работает идеально. Что изменилось?» |

> **Правило:** подготовьте план вопросов, но не читайте с листа. План — это страховка и ориентир, а не жёсткий сценарий.

### 3.5. Проведение интервью: три этапа

**Открытие:**
- Представьтесь, объясните цель встречи, обозначьте регламент по времени.
- Договоритесь о конфиденциальности.
- Создайте атмосферу доверия.

**Основная часть:**
- Следуйте структуре вопросов, но будьте гибкими.
- Если разговор уходит в сторону и это ценно — дайте ему уйти.
- Слушайте больше, чем говорите.

**Закрытие:**
- Резюмируйте услышанное вслух.
- Договоритесь о следующих шагах: кто, что и в какой срок делает после встречи.

**Принцип Парето в интервью:**
- **80%** — говорит респондент.
- **20%** — говорите вы (вопросы, уточнения, короткие резюме).

### 3.6. Навыки активного слушания

Активное слушание — это не молчание. Это набор конкретных техник:

1. **Уточнение** — «Правильно ли я понял, что...» — проверяете своё понимание и даёте собеседнику возможность скорректировать вас.
2. **Перефразирование** — «То есть, когда вы говорите "долго", вы имеете в виду примерно час?» — переводите расплывчатые слова в конкретику.
3. **Отражение эмоций** — «Похоже, этот момент вас сильно беспокоит» — признание эмоций открывает более глубокий разговор о сути проблемы.
4. **Невербальные сигналы** — кивки, зрительный контакт, открытая поза и паузы сигнализируют: вы здесь, вы слушаете, вам интересно.

> **Самое сложное в активном слушании — держать паузу и не заполнять её собственными словами. Молчание — это инструмент.**

### 3.7. Типичные ошибки интервьюера

| Ошибка                        | Описание                                                                                                      |
|-------------------------------|---------------------------------------------------------------------------------------------------------------|
| **Наводящие вопросы**         | «Вам ведь неудобно работать с этой формой?» — вы получаете подтверждение своей гипотезы, а не реальный ответ. |
| **Перебивание и спешка**      | Прерываете рассказ и торопитесь к выводам — теряете детали, которые могли изменить всю картину.               |
| **Уход в технические детали** | На этапе сбора требований обсуждать реализацию — значит закрывать дверь перед важными бизнес-контекстами.     |
| **Отсутствие фиксации**       | Надеяться на память — профессиональная ошибка. Детали теряются уже через час после встречи.                   |
| **Разговор не с тем**         | Собеседник не является реальным пользователем процесса — вы получаете чужое мнение вместо живого опыта.       |

### 3.8. Фиксация договорённостей на встрече

**Принцип устного резюме:**
В конце каждой встречи обязательно произнесите вслух: «Я услышал три главных пункта…» Это не формальность — это главная защита от недопонимания. Устное резюме снижает риск расхождений в интерпретациях на порядок.

**Что фиксировать во время разговора:**
- Ключевые тезисы и цифры — сразу, в процессе беседы.
- Открытые вопросы, на которые нет ответа здесь и сейчас.
- Противоречия — пометьте их особо.
- Договорённости о следующих шагах.

**После встречи:**
Договоритесь: кто, что и в какой срок пришлёт подтверждение или уточнение. Без конкретного ответственного договорённость остаётся намерением.

### 3.9. Протоколирование встречи

Протокол — это не стенограмма и не бюрократическая формальность. Это структурированный инструмент командной памяти, к которому возвращаются через неделю и всё понимают.

**Структура протокола:**
1. **Шапка документа** — дата, участники встречи, цель встречи.
2. **Ключевые тезисы** — главное из обсуждения, сжато, по существу.
3. **Принятые решения** — что было согласовано и зафиксировано как договорённость.
4. **Открытые вопросы** — что осталось неясным и требует уточнения.
5. **Следующие шаги** — кто, что и в какой срок делает.

> **Протокол должен быть отправлен участникам в течение 24 часов — пока информация свежа и воспоминания совпадают.**

### 3.10. Анализ материалов: от протокола к уточнениям и гипотезам

Анализ начинается после интервью. Перечитайте протокол и пройдитесь маркерами трёх цветов — это простой и мощный метод структурирования.

| Цвет        | Что означает                                                                                          | Что рождается                                    |
|-------------|-------------------------------------------------------------------------------------------------------|--------------------------------------------------|
| **Зелёный** | Зафиксированные факты и требования. То, в чём вы уверены и что можно использовать как входные данные. | —                                                |
| **Жёлтый**  | Моменты, требующие уточнения. «Здесь непонятно, какое именно значение».                               | Уточняющие вопросы для следующего контакта.      |
| **Красный** | Противоречия. «В первой части сказано одно, во второй — другое».                                      | Гипотезы, которые требуют проверки и обсуждения. |

Такой разбор превращает сырой протокол в структурированный список задач: что уточнить, что проверить, с кем переговорить повторно.

### 3.11. Источники требований

Каждое требование должно иметь источник. Если источник неизвестен — это не требование, а чьё-то пожелание.

| Источник                 | Что даёт                                               |
|--------------------------|--------------------------------------------------------|
| **Пользователи**         | Потребности, боли, ожидания от системы                 |
| **Бизнес**               | Стратегические цели, KPI, бюджетные ограничения        |
| **Регуляторы**           | Законы, стандарты, отраслевые нормы                    |
| **Существующая система** | Функциональность, которую нужно сохранить или заменить |
| **Команда разработки**   | Технические ограничения и возможности                  |

### 3.12. Шесть источников информации и триангуляция

| Источник                            | Что даёт                                                   |
|-------------------------------------|------------------------------------------------------------|
| **Интервью**                        | Скрытые потребности, мотивы, неочевидный контекст          |
| **Наблюдение**                      | Реальное поведение пользователей, «как есть на самом деле» |
| **Документы и регламенты**          | Формальная картина, SLA, нормативы, отраслевые стандарты   |
| **Переписка и коммуникации**        | История решений, путь к документу, подводные камни         |
| **Существующие материалы и данные** | Логи, дампы, старая документация, скриншоты                |
| **Пользовательские запросы**        | Тикеты, обращения в поддержку, баг-репорты, записи звонков |

**Метод триангуляции:**
Триангуляция — это перекрёстная проверка информации из трёх и более независимых источников. Только совпадение данных из разных каналов даёт аналитику уверенность в достоверности требования.

**Формула уверенности:** Интервью + Наблюдение + Данные из системы = достоверность требования. Каждый источник в отдельности несёт собственные искажения — только их пересечение даёт объективную картину.

**Пример триангуляции:**
- 🎤 Интервью: «Операция занимает около минуты».
- 👁 Наблюдение: пользователь постоянно переключается между окнами и отвлекается.
- 📊 Логи системы: система отвечает за 200 миллисекунд — производительность в норме.
- ✅ **Вывод:** проблема не в производительности системы, а в переключении внимания пользователя. Без перекрёстной проверки была бы поставлена задача на оптимизацию не того, что нужно.

### 3.13. Сложные респонденты и работа с ними

| Тип респондента              | Поведение             | Тактика                                                  |
|------------------------------|-----------------------|----------------------------------------------------------|
| **Уклончивый**               | Уходит в общие фразы  | Задавать конкретные вопросы, просить примеры             |
| **Многословный**             | Уводит в истории      | Мягко возвращать к теме, резюмировать                    |
| **Защищающийся**             | Преуменьшает проблему | Не давить, использовать сценарные вопросы                |
| **Эмоционально вовлечённый** | Жалуется, раздражён   | Дать выговориться, отразить эмоции, затем уточнить факты |
| **Самоуверенный эксперт**    | Много терминов        | Просить объяснить простыми словами, проверять по данным  |

### 3.14. Эффект Хоторна

Эффект Хоторна — люди меняют поведение, зная, что за ними наблюдают. Это важно учитывать при интервью и наблюдении: респондент может говорить «как правильно», а не «как есть на самом деле».

### 3.15. Типичные ошибки при сборе информации

1. Некорректные формулировки вопросов (наводящие, двойные).
2. Неправильный порядок сбора.
3. Опора на один источник без проверки.
4. Формальная триангуляция «для галочки».
5. Смешение целей и методов.
6. Игнорирование пользовательских запросов и логов в пользу мнения экспертов.

### 3.16. Пять шагов в рамках сбора информации

1. Определить цель.
2. Сопоставить цель с источниками.
3. Выбрать методы и респондентов.
4. Определить последовательность.
5. Заложить триангуляцию заранее.

### 3.17. Глоссарий по сбору информации

- **Респондент** — опрашиваемый; человек, у которого аналитик получает информацию.
- **ЛПР** — лицо, принимающее решение.
- **Стейкхолдер** — заинтересованная сторона, влияет на процесс или зависит от него.
- **Бенчмаркинг** — изучение того, как задача решена в других компаниях/продуктах.
- **Триангуляция** — перекрёстная проверка утверждения минимум по 2–3 независимым источникам.
- **Эффект Хоторна** — люди меняют поведение, зная, что за ними наблюдают.

## 4. Требования: виды, качество, структурирование

### 4.1. Что такое требование

**Требование** — это формализованное описание того, что система должна делать или какими свойствами обладать.

Без классификации «кнопка должна быть зелёной» соседствует с «система должна выдерживать тысячу пользователей» в одном плоском списке. Классификация даёт:
- **Ничего не упустить** — структуру и покрытие.
- **Правильные вопросы** — категории помогают знать, о чём спрашивать.
- **Единый язык** — все участники говорят об одном и том же.

### 4.2. Две большие группы требований

| Функциональные          | Нефункциональные                   |
|-------------------------|------------------------------------|
| **Что система делает?** | **Как хорошо система это делает?** |
| Поведение и сценарии    | Производительность                 |
| Бизнес-правила          | Безопасность                       |
| Обработка ошибок        | Надёжность                         |
| Интеграции и роли       | Масштабируемость                   |

> **Обе группы одинаково важны.** Система, которая работает быстро, но не делает нужного — бесполезна. И наоборот.

### 4.3. Функциональные требования: глубже

1. **Сценарии использования** — основной, альтернативные и ошибочные потоки.
2. **Бизнес-правила** — «Заказ свыше 100 000 ₽ требует подтверждения руководителя».
3. **Валидация и ограничения** — «Номер телефона должен соответствовать маске +7 (XXX) XXX-XX-XX».
4. **Интеграции и ролевая модель** — REST API в CRM; администратор удаляет, оператор — только просматривает.

**Результат:** понятный набор функций, который можно оценить, запланировать и протестировать.

### 4.4. Нефункциональные требования: категории

| Категория                  | Что включает                                          | Пример                                                                               |
|----------------------------|-------------------------------------------------------|--------------------------------------------------------------------------------------|
| **Производительность**     | Время отклика, пропускная способность, время загрузки | Время отклика — не более 300 мс при нагрузке 1000 пользователей                      |
| **Надёжность**             | Время аптайма, время восстановления                   | 99,9% — до 8 часов 46 минут простоя в год; 99,99% — не более 52 минут                |
| **Безопасность**           | Аутентификация, шифрование, аудит                     | PCI DSS, 152-ФЗ                                                                      |
| **Удобство использования** | Клики на операцию, время обучения                     | 75% пользователей осваивают интерфейс за 3 дня                                       |
| **Масштабируемость**       | Рост под нагрузкой                                    | Система должна выдерживать рост числа пользователей на 50% без изменения архитектуры |
| **Ограничения**            | Платформа, стек, юридические требования               | Поддержка последних двух версий Chrome, Safari, Firefox                              |

> **Нефункциональные требования часто недооценивают — а именно они определяют архитектуру системы. Каждая категория должна быть измерима: не «система должна быть быстрой», а «время отклика — не более 300 мс при нагрузке 1000 пользователей».**

### 4.5. Уровни требований

| Уровень                     | Пример                                  |
|-----------------------------|-----------------------------------------|
| **Бизнес-требование**       | Увеличить повторные продажи             |
| **Требование стейкхолдера** | Клиент видит историю заказов            |
| **Системное требование**    | Система отображает заказы за 12 месяцев |

Могут возникать противоречия между уровнями — отслеживаем и уточняем.

### 4.6. Бизнес-правила

| Тип правила             | Описание      | Пример                                                                            |
|-------------------------|---------------|-----------------------------------------------------------------------------------|
| **Правила-ограничения** | «Нельзя»      | «Заказ нельзя оформить без подтверждённого номера телефона»                       |
| **Правила-вычисления**  | «Как считать» | «Скидка 10% применяется, если сумма заказа больше 5000 рублей»                    |
| **Правила-выводы**      | «Если-то»     | «Если клиент не оплатил заказ в течение 24 часов, заказ автоматически отменяется» |

**Как работать с бизнес-правилами:**
1. Соберите правила из кейса и общения с заказчиком.
2. Определите тип — ограничение, вычисление, вывод.
3. Подумайте, как правило влияет на структуру данных:
   - Ограничение уникальности (email) → поле unique.
   - Диапазон значений (оценка 0–100) → check constraint.
   - Обязательность поля → not null.
4. Зафиксируйте правило в документации и передайте разработчику.

### 4.7. Критерии качества требований: INVEST

| Критерий        | Значение                                    |
|-----------------|---------------------------------------------|
| **Independent** | Реализуемо независимо от других             |
| **Negotiable**  | Задаёт поведение, не диктует реализацию     |
| **Valuable**    | Несёт ценность для бизнеса или пользователя |
| **Estimable**   | Можно оценить по трудозатратам              |
| **Small**       | Умещается в одну итерацию                   |
| **Testable**    | Есть чёткие критерии приёмки                |

> **INVEST — это фильтр. Прогоните требования через шесть критериев и увидите, какие не дотягивают.**

### 4.8. Дополнительные критерии качества

- **Атомарность** — одно требование — одна вещь. Без союза «и».
- **Однозначность** — два разработчика — одинаковое решение.
- **Необходимость** — действительно нужно, не «было бы неплохо».
- **Реализуемость** — технически возможно в рамках бюджета и сроков.
- **Прослеживаемость** — связано с источником и бизнес-целью.

### 4.9. Типичные проблемы требований

| Проблема                        | Описание                                          | Решение                                     |
|---------------------------------|---------------------------------------------------|---------------------------------------------|
| **Золотое покрытие**            | Требования «красиво звучат», но не несут ценности | Фильтр: «Какую проблему решает?»            |
| **Размытые формулировки**       | «Быстро», «удобно», «гибко»                       | Замена: измеримые показатели                |
| **Преждевременная детализация** | «Как» вместо «что»                                | Разделять поведение и реализацию            |
| **Забытые граничные случаи**    | Только «солнечный» сценарий                       | Добавлять альтернативные и ошибочные потоки |
| **Разрыв требований**           | Изменение не отражается в связанных               | Использовать трассировку                    |

### 4.10. Пять типов проблем в требованиях

1. **Противоречия** — два требования, которые не могут быть выполнены одновременно.
2. **Пробелы** — отсутствие информации, необходимой для реализации.
3. **Неоднозначности** — формулировка, которую можно понять несколькими способами.
4. **Дублирование** — одно требование описано в двух местах разными словами.
5. **Избыточность** — требования без ценности или не относящиеся к проекту.

### 4.11. Методы анализа требований

**Трассировка требований:**
Трассировка — связывание каждого требования с его источником и бизнес-целью. Инструмент: матрица трассировки.

| ID     | Описание             | Источник | Бизнес-цель   | Статус           |
|--------|----------------------|----------|---------------|------------------|
| REQ-01 | Отправка уведомлений | Заказчик | Снизить отток | ✅ Покрыто       |
| REQ-02 | Экспорт в Excel      | —        | —             | ⚠️ Нет источника |
| REQ-03 | Права доступа        | ИБ-отдел | Безопасность  | ✅ Покрыто       |

> **Требования без источника — кандидаты на удаление. Бизнес-цели без покрытия — сигнал пропуска. Трассировка — это не бюрократия, а инструмент обоснованности.**

**Проверка сценариев и граничных условий:**
- Показать сценарий по шагам.
- Задать вопросы: «Что если...», «Кто именно?», «При каких условиях?».

**Ревью с командой:**
- Разработчик и тестировщик видят технические нестыковки, которые незаметны аналитику.
- Форматы: формальная инспекция с протоколом или неформальный «свежий взгляд».

**Прототипирование:**
- Макет интерфейса вскрывает требования, которые невозможно сформулировать текстом.
- Пользователь видит макет и говорит: «А где кнопка "сохранить и продолжить"?» — это пробел.

### 4.12. Документирование результатов анализа

Результат анализа — список проблем, а не «посмотрели, вроде нормально». Каждая проблема фиксируется структурированно:

- **ID + описание** — уникальный идентификатор и чёткое описание проблемы.
- **Тип проблемы** — противоречие / пробел / неоднозначность / дублирование / избыточность.
- **Предложение и статус** — как исправить и на каком этапе устранения находится проблема.

**Инструменты:** Confluence, трекер задач, отдельный документ — главное, вести системно.

### 4.13. Структурирование требований

**Что такое структурирование:**
Структурирование — организация требований в логическую систему вместо плоского списка.

- **Группировка** — по областям и модулям.
- **Иерархия** — от целей к функциям.
- **Приоритизация** — критичное vs откладываемое.
- **Декомпозиция** — крупное → атомарное.

> **В 300 требованиях без структуры невозможно ориентироваться. Структура — это навигация.**

**Группировка требований:**
- По функциональным областям: заказы, оплата, доставка.
- По модулям системы: каталог, корзина, личный кабинет.
- По процессам: оформление, возврат, регистрация.
- По ролям: администратор, оператор, клиент.

> **Одно требование — в одной группе. Хочется положить в две? Требование слишком крупное.**

**Иерархия требований:**

Пример сверху вниз:
- Бизнес: «Увеличить повторные продажи».
- Пользователь: «Клиент видит историю заказов».
- Функция: «Система отображает заказы за 12 месяцев».

**Декомпозиция требований:**

| Уровень                   | Пример                          |
|---------------------------|---------------------------------|
| **Нельзя отменить**       | «Доработать поиск»              |
| **Нельзя измерить**       | «Улучшить поиск для всех»       |
| **Нельзя тестировать**    | «Новый поиск должен быть лучше» |
| **Не влезает в итерацию** | «Обновить весь поиск»           |

Пример декомпозиции: «Улучшить поиск» → добавление · автодополнение · сортировка · история запросов · настройки.

### 4.14. Приоритизация: метод MoSCoW

| Категория       | Описание                            |
|-----------------|-------------------------------------|
| **Must have**   | Без этого система не имеет смысла   |
| **Should have** | Важно, но можно отложить при сроках |
| **Could have**  | Желательно, если останется время    |
| **Won't have**  | Точно не в этой версии              |

> **Если всё — Must have, приоритетов нет. Must have ≤ 60% бэклога.**

### 4.15. Способы фиксации требований

| Формат                                          | Когда использовать                          |
|-------------------------------------------------|---------------------------------------------|
| **Пользовательская история и критерии приёмки** | Agile-команды                               |
| **Прецедент использования (Use Case)**          | Сложные сценарии с альтернативными потоками |
| **Спецификация требований к ПО (SRS)**          | Полная документация, единый источник истины |
| **Диаграммы BPMN и UML**                        | Визуальные процессы                         |
| **Прототипы и макеты**                          | Быстрая обратная связь до разработки        |

> **Выбор формата зависит от методологии команды и сложности системы. Можно комбинировать.**

### 4.16. Матрица трассировки требований

| ID требования | Бизнес-цель                            | Источник (стейкхолдер)       | Требование                                 | Тест-кейс                                              |
|---------------|----------------------------------------|------------------------------|--------------------------------------------|--------------------------------------------------------|
| R-01          | Снизить потерю интереса клиента        | Клиент, форма обратной связи | Добавление товара в избранное с карточки   | TC-01: добавить товар, проверить появление в списке    |
| R-08          | Соответствие требованиям приватности   | Служба безопасности          | Список избранного виден только владельцу   | TC-08: попытка открыть чужой список по прямой ссылке   |
| R-06          | Дать продукту данные для приоритизации | Менеджер по продукту         | Выгрузка отчёта по популярности избранного | TC-06: сформировать отчёт, сверить с тестовыми данными |

### 4.17. Аналитические шаблоны

**Что включаем в шаблон:**
- Реестры: подготовка и требования.
- Матрица трассировки требований.
- Диаграммы (какие: специфика задачи и проекта).
- Описание логики.
- Use Case, User Story.
- Дополнительная информация: контакты, шаблоны, задачи.

**Принципы:**
- Зависит от команды, но стремимся к унификации.
- Изменяются со временем.
- Нет фиксированной структуры: если видите, что есть проблемы — адаптируйте.

### 4.18. Итоги по требованиям

1. **Две обязательные группы** — функциональные и нефункциональные требования, обе одинаково важны.
2. **Комбинируйте подходы** — спросили → наблюдали → показали прототип → уточнили.
3. **Источник и формат обязательны** — каждое требование должно иметь источник и быть зафиксировано.
4. **Роль аналитика** — не просто записывает пожелания, а выявляет, проверяет и формализует требования.

## 5. Процессное моделирование: AS-IS и TO-BE

### 5.1. Суть AS-IS и TO-BE

|                         | AS-IS («как есть»)                                                                                      | TO-BE («как будет»)                                                  |
|-------------------------|---------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------|
| **Что это**             | Модель процесса в текущем, фактическом состоянии                                                        | Модель процесса в целевом состоянии после изменений                  |
| **Что фиксируем**       | Не то, что в регламенте, а то, что происходит на самом деле — с обходными путями и неписаными правилами | Реалистичный план с учётом достижимого, а не мечта без ограничений   |
| **Уровень детализации** | Подробно, со всеми исключениями и обходными путями                                                      | Изначально более крупно, детализация приходит по ходу проектирования |

> **Между AS-IS и TO-BE может быть несколько промежуточных версий TO-BE.**

### 5.2. Пример: подписание договора

| AS-IS                                                              | TO-BE                                                         |
|--------------------------------------------------------------------|---------------------------------------------------------------|
| Менеджер печатает договор и несёт на подпись финансовому директору | Договор формируется в системе документооборота из шаблона     |
| Юрист согласует всегда, даже типовые договоры                      | Юрист согласует только нетиповые договоры                     |
| Менеджер сканирует и вручную рассылает копии                       | Подписание электронной подписью, система сама рассылает копии |

### 5.3. Зачем нужны оба состояния

- Без AS-IS не видно, что именно менять.
- AS-IS — база для оценки эффекта изменений.
- AS-IS вскрывает скрытые зависимости между шагами.
- AS-IS — переговорная позиция с бизнесом.
- Без TO-BE улучшения рискуют быть локальными и противоречить друг другу.

### 5.4. Какие процессы выбираем

- Частота выполнения процесса.
- Влияние на бизнес.
- Острота проблемы для участников.
- Стратегическая важность.
- Готовность организации к изменениям.

### 5.5. Типичные ошибки при описании AS-IS

1. Описывают «как должно быть», а не то, что происходит на самом деле.
2. Идеализация от неловкости перед аналитиком.
3. Слишком быстрый переход к решениям.
4. Игнорирование исключений и редких случаев.
5. Один источник вместо нескольких.

### 5.6. Как проектируют TO-BE

**Источники:** цели бизнеса, результаты AS-IS, бенчмаркинг, ограничения, стейкхолдеры.

**Ограничения** (бюджет, сроки, технологии) — без них TO-BE нереализуем.

**Подходы:**
- **Инкрементальное улучшение** — точечные правки, быстрее и дешевле.
- **Реинжиниринг** — процесс проектируется заново, больше свободы, но дороже и рискованнее.

> **В AS-IS аналитик фиксирует реальность, в TO-BE — соавтор решения.**

### 5.7. Типичные ошибки при проектировании TO-BE

1. Отвечает на конкретные проблемы AS-IS.
2. Реалистично достижим с учётом ограничений.
3. Измерим — понятно, по каким метрикам виден эффект.
4. Не создаёт новых узких мест взамен старых.
5. Согласован со смежными процессами.

### 5.8. Критерии качества TO-BE

1. Отвечает на конкретные проблемы AS-IS.
2. Реалистично достижим.
3. Измерим (учитываем метрики).
4. Не создаёт новых узких мест взамен старых.
5. Согласован со смежными процессами.

### 5.9. SIPOC-подход

SIPOC — способ кратко описать процесс: Поставщик → Вход → Процесс → Выход → Клиент (Потребитель). Помогает обозначить, что входит в зону анализа, а что нет.

| Supplier        | Input                | Process                                                                 | Output          | Customer |
|-----------------|----------------------|-------------------------------------------------------------------------|-----------------|----------|
| Поставщик зерён | Кофейные зерна, вода | Клиент делает заказ → бариста готовит напиток → клиент забирает напиток | Готовый напиток | Клиент   |

**Порядок заполнения:** сначала Process, затем Outputs, Customers, Inputs, Suppliers.

### 5.10. Value Stream Mapping (VSM)

Для каждого шага AS-IS указываем:
- **Время выполнения** — сколько времени занимает сам шаг (активная работа).
- **Время ожидания** — сколько времени шаг просто «висит» в очереди, пока кто-то не начнёт его делать.
- **Создаёт ли шаг ценность** — если нет, можно подумать об удалении шага, а не об автоматизации.

| Шаг                     | Время выполнения | Время ожидания     | Создает ценность |
|-------------------------|------------------|--------------------|------------------|
| Клиент делает заказ     | 1 минута         | —                  | Да               |
| Бариста готовит напиток | 3 минуты         | 2 минуты (очередь) | Да               |

### 5.11. Метрики процессов

**Из шести метрик-кандидатов выбираем те, что уместны для процесса, и объясняем почему:**

1. **Lead time** — время от подтверждения оффера до полной готовности сотрудника.
2. **Cycle time шага** «подготовка техники».
3. **Throughput** — сколько новых сотрудников проходит процесс найма за квартал.
4. **Доля случаев**, когда сотрудник вышел без готового рабочего места в первый день.
5. **Уровень удовлетворённости** процессом найма у новых сотрудников.
6. **Доля заявок на технику**, отправленных в течение суток после подтверждения оффера.

**Правила выбора метрик:**
- Метрика должна быть привязана к проблеме, которую мы решаем.
- Не бери метрики, на которые ты не можешь повлиять.
- Хорошие метрики: «доля заявок, отправленных в первые сутки», «время от оффера до готового рабочего места».
- Плохие метрики: «количество новых сотрудников за квартал», «удовлетворённость».

### 5.12. Анализ узких мест процесса

**Узкое место** — шаг, который тормозит весь процесс, создаёт очередь или задержку.

**Признаки узкого места:**
- Длительное ожидание между шагами.
- Высокая загрузка одного участника.
- Повторный ввод одних и тех же данных.

**Пример:** Менеджер тратит час в день на ручную проверку дубликатов заявок — очевидный кандидат на автоматизацию.

### 5.13. Gap-анализ

**Gap-анализ** — сопоставление AS-IS и TO-BE шаг за шагом. Разрыв в трёх измерениях: люди, процесс, технологии. Результат — основа дорожной карты перехода.

| AS IS                              | TO BE                                           | Что меняется                                                                |
|------------------------------------|-------------------------------------------------|-----------------------------------------------------------------------------|
| Юрист согласует всегда             | Юрист согласует только нетиповые договоры       | В процесс, люди: добавлено условие, шаг стал вероятностным                  |
| Бумажный документ, ручная передача | Электронный документ в системе документооборота | В процесс, технологии: нужна новая система, исчезает физическое перемещение |
| Ручная рассылка копий по почте     | Автоматическая рассылка системой                | В процесс: действие автоматизировано, риск «забыли отправить» уходит        |

> **Переход не всегда одним релизом — возможны промежуточные состояния.**

### 5.14. Точки автоматизации

**Точка автоматизации** — конкретное место в бизнес-процессе, где ручной труд заменяется или дополняется работой системы.

**Что можно автоматизировать:**
- Вычисления и расчёты.
- Проверки и валидацию данных.
- Передачу данных между участниками.
- Уведомления и напоминания.
- Формирование документов.
- Сбор и агрегацию данных.

**Признаки для поиска точек автоматизации:**

| Признак                  | Описание                         |
|--------------------------|----------------------------------|
| **Повторяемость**        | Регулярно повторяющиеся действия |
| **Формализуемость**      | Наличие чёткого алгоритма        |
| **Высокие затраты**      | Занимает много времени           |
| **Склонность к ошибкам** | Частые сбои и неточности         |

> **Не всё нужно автоматизировать. Творческие решения, переговоры и сложные экспертные оценки — остаются за человеком.**

### 5.15. Пять подходов к выявлению точек автоматизации

1. **Узкие места** — где дольше всего ждут.
2. **Повторяющиеся операции** — стабильный алгоритм, низкая вариативность, большой объём.
3. **Передача данных** — ручная пересылка, двойной ввод, потеря данных.
4. **Ошибки и переделки** — частые возвраты, жалобы, повторные проверки.
5. **Сравнение As-Is и To-Be** — каждый шаг, который в To-Be переходит к системе.

### 5.16. Источники сигналов для автоматизации

- **Прямой вопрос исполнителям** — не «опишите процесс», а «что вас утомляет каждый день».
- **Process mining** — восстанавливает реальный процесс из логов систем, а не из слов людей.
- **Бенчмаркинг** — как аналогичная задача решена у конкурентов или в отрасли.

### 5.17. Виды автоматизации

| Вид                              | Описание                                                                                           |
|----------------------------------|----------------------------------------------------------------------------------------------------|
| **RPA**                          | Робот повторяет действия человека в интерфейсе, не требует API, но это «костыль» поверх интерфейса |
| **Интеграция через API**         | Надёжнее и быстрее в работе, но нужен сам API и ресурсы на разработку                              |
| **Готовые SaaS/no-code решения** | Быстро, но только для типовых задач                                                                |
| **Кастомная разработка**         | Самый гибкий, но самый долгий и дорогой вариант                                                    |

### 5.18. Степень вовлечённости человека

- **Полная автоматизация** — система выполняет шаг целиком.
- **Human-in-the-loop** — система готовит решение, человек утверждает.
- **Подсказка системы** — система предлагает вариант, решение остаётся за человеком.

> **Выбор уровня зависит от цены ошибки и организационной готовности.**

### 5.19. Целесообразность автоматизации: три критерия

| Критерий                     | Вопрос                                                      |
|------------------------------|-------------------------------------------------------------|
| **Технически осуществимо**   | Есть ли доступ к системам и данным                          |
| **Экономически оправдано**   | Затраты соразмерны объёму операций и цене ручного труда     |
| **Организационно приемлемо** | Люди готовы принять изменение, и есть кому его поддерживать |

> **Точка, прошедшая только 1–2 критерия — кандидат на «не сейчас».**

### 5.20. Приоритизация точек автоматизации

|                       | Высокий эффект                    | Низкий эффект    |
|-----------------------|-----------------------------------|------------------|
| **Низкая сложность**  | **Быстрые победы.** Начать здесь. | **Опционально.** |
| **Высокая сложность** | **Стратегические проекты.**       | **Избегать.**    |

**Критерии приоритизации:**
- Влияние на скорость процесса.
- Влияние на качество результата.
- Частота выполнения операции.
- Стоимость и риски реализации.

> **Правило: сначала автоматизируем то, что даёт максимальный результат минимальными усилиями.**

### 5.21. Подготовка аналитических материалов по точке автоматизации

По каждой точке автоматизации необходимо подготовить структурированное описание:

1. **Текущее состояние** — как выполняется шаг сейчас, кто участвует, какие инструменты используются.
2. **Проблема** — почему текущее состояние не устраивает: потери времени, ошибки, затраты.
3. **Предлагаемое решение** — что именно будет делать система вместо человека или в дополнение к нему.
4. **Ожидаемый эффект** — что изменится: скорость, качество, стоимость операции.
5. **Оценка затрат** — примерная сложность реализации и ресурсы, необходимые для внедрения.

### 5.22. Типичные ошибки при выявлении точек автоматизации

1. **Автоматизация ради автоматизации** — автоматизируем шаг, который не является реальной проблемой.
2. **Игнорирование исключений** — описали «счастливый путь», забыли про обработку ошибок.
3. **Преждевременное проектирование** — сразу рисуем интерфейс, не обосновав необходимость.
4. **Автоматизация хаоса** — пытаемся автоматизировать неэффективный процесс.
5. **Забытые пользователи** — не учли, кто будет работать с автоматизированным шагом.

### 5.23. Итоги по процессному моделированию

- AS-IS фиксирует реальность, TO-BE проектирует решение.
- AS-IS подробно, TO-BE крупными мазками.
- Приоритизация процессов — до сбора данных.
- TO-BE должен быть реалистичным и измеримым.
- Gap-анализ — связующее звено между двумя моделями.
- Не автоматизируйте хаос. Сначала наведите порядок в процессе — потом передавайте его системе.

## 6. Пользовательские роли, цели и сценарии

### 6.1. Почему начинаем с пользователей

Система создаётся не ради технологий — ради людей, которые с ней работают. Пропуск роли на старте означает потерянный функционал и дорогостоящие переделки.

- **Приоритизация** — понимание целей пользователя даёт чёткие критерии для расстановки приоритетов требований.
- **Архитектура** — точки взаимодействия определяют архитектуру интерфейсов и интеграций с самого начала.

### 6.2. Что такое пользовательская роль

**Роль** — это набор обязанностей и прав в контексте системы. Роль описывает поведение, а не личность и не должность.

> **Важно:** один человек может играть несколько ролей, и одну роль могут исполнять разные люди.

**Пример:**
- «Менеджер по продажам» — это должность.
- «Создатель заявок», «Согласующий», «Аналитик отчётов» — это роли.

**Роли выявляются из бизнес-процессов, а не из штатного расписания.**

### 6.3. Как выявлять пользовательские роли

**Источники:**
- Анализ бизнес-процессов.
- Интервью со стейкхолдерами.
- Наблюдение операций на месте.
- Анализ унаследованной системы.

**Финальный шаг** — группировка: объединяем похожих пользователей по целям и правам доступа. Результат — список ролей с кратким описанием.

### 6.4. Цели и задачи пользователей

|                  | Цель — «Зачем?»                                         | Задача — «Что сделать?»                    |
|------------------|---------------------------------------------------------|--------------------------------------------|
| **Что это**      | Желаемый результат, которого пользователь хочет достичь | Конкретный шаг на пути к цели              |
| **Стабильность** | Стабильна и не зависит от реализации                    | Может меняться в зависимости от интерфейса |

**Пример:**
- Цель: «Быть в курсе статуса заказов».
- Задачи: просмотреть список заказов, отфильтровать по статусу, открыть детали заказа.

> **Цели стабильны — задачи могут меняться при изменении реализации.**

### 6.5. Как формулировать цели пользователей

**Хорошая цель:**
«Как менеджер, я хочу видеть просроченные заказы, чтобы вовремя эскалировать проблему» — сформулирована от лица пользователя, на его языке.

**Плохая цель:**
«Система должна выдавать отчёт по заказам с фильтром по дате» — это про систему, а не про пользователя. Технических деталей в цели быть не должно.

**Источники:** интервью, наблюдение, анализ боли пользователя. Результат — список целей, обосновывающий функциональные требования.

### 6.6. Карта пользовательских ролей и целей

Таблица, где строки — роли, столбцы — цели. На пересечении отмечаем, какая роль какую цель преследует.

**Позволяет увидеть:**
- Все ли роли учтены.
- Все ли цели покрыты.
- Нет ли конфликта интересов.

**Конфликт:** «Оператор хочет быстрее оформить заказ» vs «Специалист по рискам хочет больше проверок». Выявляйте и разрешайте на старте.

### 6.7. Точки взаимодействия с системой (Touchpoints)

**Touchpoint** — это место и способ контакта пользователя с системой. Это не только экран приложения.

| Тип                  | Пример                                            |
|----------------------|---------------------------------------------------|
| **Интерфейс**        | Веб-приложение, мобильное приложение, форма ввода |
| **Уведомления**      | Email, push-уведомление, SMS, системный алерт     |
| **API и интеграции** | Машинный обмен данными, экспорт, печатная форма   |

### 6.8. Как выявлять точки взаимодействия

**Ключевые вопросы:**
- Как пользователь узнаёт о результате?
- Где он видит ошибку или предупреждение?
- Что происходит вне экрана?
- Через что взаимодействует сейчас?

**Результат** — список touchpoint'ов с описанием контекста и канала коммуникации.

### 6.9. Типы точек взаимодействия

| Тип           | Описание                                                                                   |
|---------------|--------------------------------------------------------------------------------------------|
| **Прямые**    | Пользователь активно инициирует контакт: открывает приложение, нажимает кнопку             |
| **Косвенные** | Система обращается к пользователю: уведомления, письма, алерты                             |
| **Фоновые**   | Система действует без участия пользователя: автообновление статуса, ночная выгрузка отчёта |
| **Смежные**   | Через другой инструмент: интеграция с календарём, экспорт в Excel                          |

> **Каждый тип требует своего подхода к проектированию и отдельного описания в требованиях.**

### 6.10. Роли, цели и touchpoint'ы в жизненном цикле требований

Три элемента формируют верхний уровень требований, из которого вырастает вся детализация:

- **Роли** — для кого мы проектируем.
- **Цели** — зачем нужны конкретные функции.
- **Touchpoint'ы** — где и как система встречается с пользователем.

> **Если роли не выявлены — требования висят в воздухе без привязки к реальным людям.**

### 6.11. Что такое сценарий использования

**Сценарий (поток событий)** — последовательность шагов, которую выполняет пользователь или система для достижения конкретного результата.

**Происхождение:** пришёл из методологии Use Cases, активно используется и в User Stories. Описывает поведение системы в ответ на действия пользователя.

**Ключевой вопрос:** «Что происходит шаг за шагом, когда пользователь взаимодействует с системой?» Это не код и не архитектура — это поведение, видимое пользователю.

> **Хороший сценарий понятен разработчику, тестировщику и заказчику одновременно.**

### 6.12. Три типа сценариев

| Тип                | Описание                                                                                                    | Результат          |
|--------------------|-------------------------------------------------------------------------------------------------------------|--------------------|
| **Основной**       | «Солнечный день» — всё идёт по плану. Пользователь достигает цели без помех.                                | Цель достигнута    |
| **Альтернативный** | Пользователь достигает цели, но другим путём. Это не ошибка — это вариация, предусмотренная бизнес-логикой. | Цель достигнута    |
| **Исключительный** | Пользователь не достигает цели — что-то пошло не так. Возникает ошибка или непреодолимое препятствие.       | Цель не достигнута |

> **Правило полноты:** на каждый основной сценарий должен быть хотя бы один альтернативный и хотя бы один исключительный. Только три типа вместе дают полную картину поведения системы.

### 6.13. Основной сценарий — «Солнечный день»

**Что это:** самый прямой и ожидаемый путь к цели. Все шаги выполняются успешно, все условия соблюдены, система отвечает корректно на каждое действие пользователя.

**Роль основного сценария:** это каркас, на который нанизываются все остальные потоки. Именно он задаёт структуру и нумерацию шагов, к которым привязываются альтернативы и исключения.

**Пример:** Оформление заказа в интернет-магазине. Пользователь авторизован, товар в наличии, платёж проходит с первой попытки, заказ создан.

> **Правило:** основной сценарий пишется первым. Пока нет основного — нет смысла описывать отклонения.

### 6.14. Альтернативный сценарий — другой путь к той же цели

Пользователь достигает цели, но идёт другим путём или при других условиях. Это не ошибка — это вариация, предусмотренная бизнес-логикой системы.

**Примеры:**
- Пользователь вводит промокод на странице оформления — система пересчитывает стоимость и продолжает поток.
- Пользователь выбирает курьерскую доставку вместо самовывоза — система запрашивает адрес доставки.
- Пользователь оплачивает картой, а не наличными при получении — система направляет на платёжный шлюз.
- У пользователя есть сохранённый адрес доставки — система подставляет его автоматически.

**Вопрос для выявления:** «Какие ещё варианты достижения цели есть у пользователя?»

### 6.15. Исключительный сценарий — цель не достигнута

Пользователь не достигает цели. Возникает ошибка или непреодолимое препятствие. Это принципиальное отличие от альтернативного сценария — результат не получен.

> **Исключительные сценарии — самая недооценённая часть требований. Их чаще всего забывают описать, хотя именно они определяют устойчивость системы.**

**Вопрос для выявления:** «Что может пойти не так? Что будет, если этот шаг завершится неудачей?»

**Примеры исключений:**
- Платёж отклонён банком.
- Пользователь не прошёл аутентификацию.
- Товар закончился на складе в момент оформления.
- Сбой базы данных при сохранении заказа.

### 6.16. Как выявлять сценарии: от основного к границам

**Шаги:**
1. Опиши главный путь.
2. Просмотри альтернативы.
3. Задокументируй сценарии.

**Вопросы для альтернатив:**
- Может ли пользователь выбрать другой вариант?
- Есть ли другие условия, при которых шаг выполнится иначе?

**Вопросы для исключений:**
- Что может пойти не так на этом шаге?
- Что если внешняя система не ответила?
- Что если данные невалидны?

### 6.17. Формат описания сценариев

**Use Case: структура**
- Имя и цель.
- Предусловия.
- Основной поток (нумерованный список).
- Альтернативные потоки (с привязкой к шагу).
- Исключительные потоки.
- Постусловия.

**User Story + Acceptance Criteria**
В критериях приёмки описываем не только основной случай, но и альтернативы и ошибки.

**Пример AC:** «При нажатии „Оплатить" отправляется запрос в шлюз. Если ответ успешный — заказ создаётся. Если ошибка — пользователь видит сообщение и кнопку „Попробовать снова".»

### 6.18. Типичные ошибки при описании сценариев

1. **Только основной сценарий** — система падает на первом же исключении.
2. **Перепутаны типы сценариев** — ошибка валидации описана как альтернатива, хотя цель не достигнута.
3. **Технический жаргон** — «Система дёргает API, парсит JSON, мапит на DTO» — заказчик и тестировщик не понимают.
4. **Неверный уровень детализации** — слишком детально или слишком абстрактно.
5. **Пропущены предусловия**.

### 6.19. Сценарии на всём жизненном цикле

| Этап               | Что происходит                                                      |
|--------------------|---------------------------------------------------------------------|
| **Анализ**         | Выявляем сценарии через интервью, наблюдение, анализ документов     |
| **Проектирование** | Детализируем шаги, добавляем системные реакции                      |
| **Разработка**     | Сценарий — основа для написания кода, реализуются все потоки        |
| **Тестирование**   | Тест-кейсы пишутся на основе всех трёх типов сценариев              |
| **Приёмка**        | Заказчик проверяет систему по сценариям, отражающим реальные задачи |

### 6.20. Пользовательские и системные сценарии

|                   | Пользовательский сценарий                                                                                     | Системный сценарий                                                                                       |
|-------------------|---------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| **Что описывает** | Последовательность действий, видимых пользователю                                                             | Последовательность действий, выполняемых системой автоматически                                          |
| **Пример**        | Пациент выбирает врача → система показывает расписание → пациент выбирает время → система подтверждает запись | Система за сутки до приёма отправляет напоминание. Если пациент не пришёл — через сутки фиксирует неявку |

### 6.21. Элементы сценария: общая структура

1. **Имя и цель** — уникальное название и ожидаемый результат.
2. **Предусловия** — что должно быть выполнено до старта сценария.
3. **Триггер** — событие, которое запускает сценарий.
4. **Потоки** — основной, альтернативные, исключительные.
5. **Постусловия** — состояние системы после завершения.

### 6.22. Факторы и предусловия

| Предусловия                                                                                        | Факторы                                                                          |
|----------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------|
| Условия, которые должны быть истинны до начала сценария. Если не выполнены — сценарий не стартует. | Внешние условия, не контролируемые системой, но влияющие на выполнение сценария. |
| Пользователь авторизован                                                                           | Загруженность канала связи                                                       |
| Корзина не пуста                                                                                   | Поведение платёжного шлюза                                                       |
| Есть права на операцию                                                                             | Доступность стороннего сервиса                                                   |

> **Предусловия выносятся отдельно — они не описываются внутри шагов сценария.**
> **Факторы объясняют, почему сценарий уходит в альтернативный или исключительный поток.**

### 6.23. Триггеры: что запускает сценарий

| Тип триггера         | Пример                                                              |
|----------------------|---------------------------------------------------------------------|
| **Пользовательский** | Нажатие кнопки, ввод данных, переход по ссылке                      |
| **Временной**        | Наступление времени или даты: ночная выгрузка, напоминание за сутки |
| **Событийный**       | Поступление платежа, ответ внешней системы, смена статуса           |
| **Системный**        | Завершение предыдущего сценария, ошибка, таймаут                    |

> **Правило:** у каждого сценария должен быть явно указан триггер. Если триггер неясен — сценарий описан неполно.

### 6.24. Основной поток: правила описания

**Примеры шагов:**
- Шаг пользователя: «Пользователь нажимает кнопку "Записаться"».
- Шаг системы: «Система проверяет доступность выбранного слота».
- Шаг с результатом: «Система отображает подтверждение записи с номером».

### 6.25. Альтернативные потоки: как описывать

Альтернативный поток — это ветвление основного. Пользователь достигает цели, но другим путём.

1. **Привязка к шагу** — «А1. На шаге 5: если пользователь выбрал оплату картой, то…» — всегда указывайте точку ветвления.
2. **Собственные шаги** — альтернативный поток содержит свои пронумерованные шаги и завершается явным возвратом.
3. **Цель достигается** — если цель не достигается, это уже исключительный поток, не альтернативный.

**Пример:** «А2. На шаге 3: если пользователь применяет промокод, система пересчитывает сумму. Возврат на шаг 6 основного потока».

### 6.26. Исключительные потоки: как описывать

| Элемент             | Описание                                               |
|---------------------|--------------------------------------------------------|
| **Условие**         | При каком именно сбое или ошибке возникает поток       |
| **Реакция системы** | Что система делает в ответ на нештатную ситуацию       |
| **Результат**       | Понятный пользователю итог — сообщение, кнопка, статус |

**Пример:** «И1. На шаге 5: если платёжный шлюз вернул отказ, система отображает сообщение с причиной и кнопку "Попробовать снова". Сценарий завершается, заказ не создан».

> **Исключительные потоки — это не баги. Это предусмотренное поведение системы при нештатных ситуациях. Каждый должен завершаться понятным результатом для пользователя.**

### 6.27. Взаимосвязи между сценариями

| Тип связи           | Описание                                                                            | Пример                                      |
|---------------------|-------------------------------------------------------------------------------------|---------------------------------------------|
| **Расширение**      | Альтернативный или исключительный поток добавляет вариативное поведение к основному | —                                           |
| **Включение**       | Один сценарий включает другой как подпрограмму                                      | «Аутентификация» — в «Запись» и в «Историю» |
| **Предшествование** | Сценарий Б выполняется только после А                                               | «Оплата» — только после «Оформления заказа» |
| **Параллельность**  | Два сценария выполняются одновременно                                               | «Отправка уведомления» и «Создание заказа»  |

### 6.28. Как документировать сценарии и взаимосвязи

**Форматы:**
1. **Диаграмма вариантов использования** — визуальная карта сценариев, актёров и связей.
2. **Диаграмма активности** — визуализация потока с ветвлениями и условиями.
3. **Текстовый шаблон** — структурированный: имя, цель, предусловия, потоки, постусловия.
4. **Картирование пользовательских историй** — карта сценариев, сгруппированная по этапам пользовательского пути.

**Как выбрать формат:**
- UML-диаграммы — для формальных спецификаций.
- Текстовый шаблон — универсален, читается всеми.
- User Story Map — для agile-команд.

> **Главное: взаимосвязи должны быть явно видны, а не угадываться.**

### 6.29. Типичные ошибки при описании сценариев

1. **Нет триггера** — непонятно, когда сценарий запускается.
2. **Пропущены предусловия** — разработчик не знает, с какого состояния начинать.
3. **Перепутаны потоки** — альтернативные и исключительные потоки смешаны.
4. **Неверный масштаб шагов** — слишком крупные или слишком мелкие.
5. **Нет возврата из ветки** — после альтернативного потока непонятно, что происходит дальше.
6. **Не описаны взаимосвязи** — сценарии дублируют друг друга или противоречат.

### 6.30. Итоги по сценариям

1. **Сценарий — это структура** — имя, цель, предусловия, триггер, потоки, постусловия. Не просто текст.
2. **Три типа потоков** — основной (идеальный путь), альтернативный (путь к цели с вариациями), исключительный (обработка ошибок).
3. **Сценарии связаны** — расширяют, включают, предшествуют, выполняются параллельно.

> **Хороший сценарий не оставляет вопросов. Если после прочтения вопросы остались — сценарий недоделан.**

## 7. Данные: сущности, атрибуты, связи, модели

### 7.1. Зачем аналитику модель данных

Любая система хранит и обрабатывает данные — это фундамент, на котором строится вся функциональность. Без модели данных требования к системе — это фасад без фундамента: красиво, но непонятно, на чём держится.

- **Единый язык** — общий словарь для команды, бизнеса и разработчиков.
- **Основа для API** — фундамент интеграций и межсистемного взаимодействия.
- **Бизнес-правила** — понимание ограничений и логики предметной области.

### 7.2. Что такое сущность

**Сущность** — это объект реального мира, о котором система хранит информацию. Это понятие предметной области на логическом уровне, а не таблица в базе данных.

> **Правило:** сущность — это существительное, значимое для бизнеса. Если объект можно сосчитать и нужно хранить данные — это сущность.

**Примеры:** Клиент, Заказ, Товар, Сотрудник, Договор, Счёт, Склад, Магазин.

**Каждая сущность должна иметь уникальный идентификатор**, однозначно отличающий один экземпляр от другого.

### 7.3. Как находить сущности

**Источники:** бизнес-процессы, пользовательские сценарии, интервью, документы и регламенты, существующие системы.

**Шаги:**
1. **Сбор существительных** — из сценариев, документов и систем.
2. **Отсеивание шумных** — удалить редкие и технические термины.
3. **Проверка ценности** — оценить бизнес-значимость и использование.
4. **Фиксация кандидатов** — занести в каталог и согласовать.

**Пример разбора:** «Клиент оформляет Заказ, содержащий Товары. Заказ доставляется по Адресу. Клиент оплачивает Заказ Платёжным документом».
- Существительные → сущности: Клиент, Заказ, Товар, Адрес, Платёжный документ.
- Глаголы → связи: оформляет, содержит, доставляется, оплачивает.

### 7.4. Что такое атрибут

**Атрибут** — характеристика сущности. Каждый атрибут имеет: имя, тип данных, обязательность, ограничения.

**Атрибуты бывают:**
- Обязательные и опциональные.
- Уникальные (не повторяются).
- Вычисляемые (рассчитываются из других).

| Клиент                 | Заказ               |
|------------------------|---------------------|
| Имя (обязательный)     | Номер (уникальный)  |
| Телефон (опциональный) | Дата создания       |
| Email (уникальный)     | Статус              |
| Дата регистрации       | Сумма (вычисляемый) |

> **Если атрибут описывает другой объект — это кандидат в отдельную сущность, а не просто поле.**

### 7.5. Уникальный идентификатор сущности

Каждая сущность должна иметь уникальный идентификатор — атрибут или комбинацию атрибутов, позволяющих однозначно найти конкретный экземпляр.

| Тип ключа             | Описание                                        | Риск                                                  |
|-----------------------|-------------------------------------------------|-------------------------------------------------------|
| **Естественный ключ** | Уникален по природе: номер паспорта, ИНН, email | Может меняться со временем                            |
| **Суррогатный ключ**  | Искусственный: порядковый номер, UUID           | Рекомендация: использовать как основной идентификатор |

### 7.6. Что такое связь

**Связь** — это ассоциация между двумя сущностями, отражающая бизнес-отношение. Связь — это всегда глагол или предлог: оформляет, содержит, работает в, находится на.

| Связь             | Пример                      |
|-------------------|-----------------------------|
| Клиент → Заказ    | Клиент оформляет Заказ      |
| Товар → Склад     | Товар находится на Складе   |
| Сотрудник → Отдел | Сотрудник работает в Отделе |

### 7.7. Типы связей по кардинальности

| Тип                  | Обозначение | Пример                                                               |
|----------------------|-------------|----------------------------------------------------------------------|
| **Один-к-одному**    | 1:1         | Сотрудник имеет один Пропуск. Пропуск принадлежит одному Сотруднику. |
| **Один-ко-многим**   | 1:M         | Клиент имеет много Заказов. Заказ принадлежит ровно одному Клиенту.  |
| **Многие-ко-многим** | M:N         | Студент записан на много Курсов. Курс содержит много Студентов.      |

> **Самый распространённый тип в реальных системах — 1:M. Связь M:N требует особой обработки при реализации в реляционной модели.**

### 7.8. Кардинальность: обязательность участия

Кардинальность указывает, сколько экземпляров одной сущности может быть связано с экземпляром другой.

| Обозначение | Значение       |
|-------------|----------------|
| \|          | Ровно один     |
| 0..1        | Ноль или один  |
| 0..*        | Ноль или много |
| 1..*        | Один или много |

**Примеры:**
- Клиент имеет 0..* Заказов. Заказ принадлежит **ровно одному** Клиенту.
- Отдел содержит 0..* Сотрудников. Сотрудник работает в **ровно одном** Отделе.
- Товар находится на 0..* Складах. На Складе хранится 0..* Товаров.

### 7.9. Связь M:N и ассоциативная сущность

Связь M:N не может быть реализована напрямую в реляционной модели. Вводится **ассоциативная сущность** — она разбивает M:N на две связи 1:M и может нести собственные атрибуты.

> **Ассоциативная сущность — важный аналитический инструмент, который часто вскрывает скрытые требования к системе.**

**Примеры ассоциативных сущностей:**
- Студент ↔ Курс → «Запись на курс» (дата записи, оценка, количество).
- Заказ ↔ Товар → «Позиция заказа» (цена, скидка, количество).

### 7.10. Первичный, внешний и составной ключ

- **Первичный ключ (PK, Primary Key)** — уникальный идентификатор сущности.
- **Внешний ключ (FK, Foreign Key)** — атрибут в одной сущности, который ссылается на первичный ключ другой сущности. Пример: Бронирование.КлиентID ссылается на Клиент.ID.
- **Составной ключ** — когда одного атрибута недостаточно, чтобы однозначно определить запись, и используется комбинация нескольких атрибутов сразу. Пример: в ассоциативной сущности БронированиеДопУслуга ни БронированиеID, ни ДопУслугаID по отдельности не уникальны, но комбинация (БронированиеID=101, ДопУслугаID=7) однозначно определяет ровно одну запись.

### 7.11. Типы данных

**Простые типы:**

| Тип                 | Описание                                                                                               | Пример                                        |
|---------------------|--------------------------------------------------------------------------------------------------------|-----------------------------------------------|
| **String**          | Произвольный текст                                                                                     | Имя, название, адрес                          |
| **Integer**         | Целое число                                                                                            | Количество, возраст, номер                    |
| **Decimal / float** | Дробное число. Для денежных сумм лучше decimal, а не float (float может давать погрешности округления) | Сумма заказа                                  |
| **Boolean**         | Логическое значение                                                                                    | true/false (да/нет, истина/ложь)              |
| **Date / datetime** | Дата, дата и время                                                                                     | Дата рождения, дата создания записи           |
| **Enum**            | Перечисление — фиксированный заранее известный список значений                                         | Статус: свободен / в аренде / на обслуживании |

**Сложные типы:**

| Тип               | Описание                                                                                     | Пример                                                         |
|-------------------|----------------------------------------------------------------------------------------------|----------------------------------------------------------------|
| **JSON**          | Вложенные объекты и списки внутри одного атрибута                                            | `{"язык": "ru", "уведомления": {"sms": true, "email": false}}` |
| **XML**           | Похожий по смыслу формат, более многословный. Встречается реже, в основном в старых системах | `<настройки><язык>ru</язык></настройки>`                       |
| **Array**         | Список значений одного типа внутри одного атрибута                                           | Фотографии: `["photo1.jpg", "photo2.jpg"]`                     |
| **Binary / blob** | Для хранения самих файлов (изображений, документов) напрямую в базе                          | —                                                              |

### 7.12. Ошибки при выделении сущностей

1. Глагол по ошибке принят за сущность.
2. Атрибут на самом деле заслуживает быть отдельной сущностью, или наоборот.
3. Забыто направление кардинальности.
4. У сущности не определён ни один идентификатор.

### 7.13. Логическая модель данных

**Логическая модель данных** — это описание данных на языке бизнеса, без привязки к конкретной СУБД или технологии хранения. Она отвечает на вопрос «какие данные нужны системе и как они связаны», а не «в каких таблицах они лежат».

**Свойства:**
- **Независимость** — модель не зависит от выбора технологии хранения.
- **Общий язык** — понятна бизнесу, аналитикам и разработчикам.
- **Основа для API** — служит фундаментом для проектирования интеграций.

**Что включает логическая модель:**
- **Сущности** — все объекты предметной области с их описанием.
- **Атрибуты** — свойства каждой сущности: типы данных и ограничения.
- **Связи** — отношения между сущностями с кардинальностью.
- **Бизнес-правила** — ограничения целостности и инварианты данных.

> **Логическая модель не содержит VARCHAR(255), индексов или решений о денормализации — это физический уровень.**

### 7.14. Уровни моделирования данных

| Уровень            | Что описывает                                                    | Кто работает                  |
|--------------------|------------------------------------------------------------------|-------------------------------|
| **Концептуальный** | Верхнеуровневые сущности и связи, обсуждение с бизнесом          | Бизнес-аналитик               |
| **Логический**     | Детальные атрибуты, типы данных, связи, бизнес-правила, без СУБД | Системный аналитик            |
| **Физический**     | Таблицы, колонки, типы данных, индексы, ограничения              | Архитектор или разработчик БД |

> **Основная зона работы аналитика — логический уровень.**

### 7.15. Бизнес-объект: определение

**Бизнес-объект** — логическая группировка данных и поведения, имеющая смысл для бизнеса. Он шире, чем просто сущность в базе данных.

| Сущность | Бизнес-объект      |
|----------|--------------------|
| Данные   | Данные + поведение |

**Примеры:** Заказ, Клиент, Счёт, Договор, Товар, Поставка, Возврат. Бизнес-объект живёт не только в БД — он перемещается между системами и участвует в процессах.

### 7.16. Структура бизнес-объекта

1. **Идентификатор** — уникальный ключ, по которому объект находят и ссылаются на него.
2. **Атрибуты** — свойства объекта: имя, статус, дата, сумма.
3. **Связи** — отношения с другими объектами: Заказ → Клиент, Заказ → Товары.
4. **Поведение** — операции: создать, изменить статус, отменить, рассчитать стоимость.
5. **Правила** — инварианты: сумма не может быть отрицательной, статус меняется по маршруту.

### 7.17. Жизненный цикл бизнес-объекта

Каждое состояние определяет, какие атрибуты доступны, какие операции разрешены и в какие состояния можно перейти. Описание жизненного цикла вскрывает бизнес-правила, которые не видны в статической модели данных.

**Пример жизненного цикла заказа:**
- **Новый** — создано, ожидает действий.
- **Подтверждён** — проверен, готов к оплате.
- **Оплачен** — оплата получена.
- **Отгружен** — передан в логистику.

### 7.18. Агрегация и композиция

|            | Агрегация                                                                                     | Композиция                                                                                    |
|------------|-----------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|
| **Суть**   | Часть может существовать независимо от целого                                                 | Часть не существует без целого                                                                |
| **Пример** | Заказ и Товар. Товар существует без конкретного заказа. Можно перенести товар в другой заказ. | Заказ и ПозицияЗаказа. Позиция не имеет смысла без заказа. Удалили заказ — позиции удалились. |

### 7.19. Бизнес-объекты в API и интеграциях

**От объекта к ресурсу:**
Каждый бизнес-объект становится ресурсом в REST API. Логическая модель — это контракт между системами.

| Операция  | HTTP-метод | Маршрут      |
|-----------|------------|--------------|
| Создать   | POST       | /orders      |
| Прочитать | GET        | /orders/{id} |
| Обновить  | PATCH      | /orders/{id} |

> **При интеграциях объект может преобразовываться: не все атрибуты передаются, формат может отличаться.**

### 7.20. Как строить логическую модель

1. **Определите границы** — какую часть бизнеса мы моделируем.
2. **Выявите бизнес-объекты** — из требований, сценариев, интервью.
3. **Опишите атрибуты и связи** — идентификатор, свойства, отношения.
4. **Опишите жизненный цикл** — состояния, переходы и разрешённые операции.
5. **Зафиксируйте бизнес-правила** — ограничения целостности, инварианты.
6. **Проверьте на сценариях** — может ли модель поддержать все описанные Use Cases.

### 7.21. Типичные ошибки

1. **Смешение уровней** — в логической модели появляются типы VARCHAR, индексы.
2. **Пропущенные правила** — модель описывает данные, но не ограничения.
3. **Игнорирование жизненного цикла** — объекты описаны статически.
4. **Модель не проверена на сценариях** — важный Use Case не поддерживается.

### 7.22. Связь модели данных с требованиями, процессами и сценариями

**Зачем связывать данные с остальными артефактами:**
Модель данных не существует в вакууме. Она обслуживает сценарии, поддерживает бизнес-правила и обеспечивает выполнение требований. Разрыв между данными и требованиями приводит к системе, где данные есть — но нужная функциональность не работает.

**Связь двусторонняя:**
- Требования определяют, какие данные нужны.
- Модель данных определяет, какие требования вообще возможны.

**Примеры:**
- «Отображать историю заказов» → Сущность Заказ: номер, дата, статус, сумма.
- «Проверять уникальность email» → Атрибут Email сущности Клиент + ограничение уникальности.

### 7.23. Проверка модели данных через требования

**Метод:** для каждого требования проверяем, есть ли в модели все необходимые сущности, атрибуты и связи. Это вскрывает пропуски на раннем этапе — до начала разработки.

**Цикл:**
1. Взять требование.
2. Проверить модель.
3. Исправить или подтвердить.

> **Если требование нельзя поддержать текущей моделью данных — модель нужно доработать.**

### 7.24. Данные и пользовательские сценарии

Каждый шаг пользовательского сценария читает, создаёт, изменяет или удаляет данные. Проходя по шагам сценария, мы видим, какие сущности задействованы и что с ними происходит.

| Сценарий              | Действия с данными                                                 |
|-----------------------|--------------------------------------------------------------------|
| **Оформление заказа** | Создаёт Заказ и Позиции, обновляет остатки Товаров, создаёт Платёж |
| **Просмотр истории**  | Читает список Заказов клиента с фильтрацией и сортировкой          |

### 7.25. CRUD-матрица: сценарии и сущности

**CRUD** — Create, Read, Update, Delete. Строки матрицы — пользовательские сценарии, столбцы — сущности, на пересечении — операции.

**Матрица выявляет:**
- Все ли сущности кем-то создаются.
- Нет ли сценариев без данных.
- Нет ли «мёртвых» сущностей.

| Сценарий          | Заказ | Позиция | Товар | Платёж |
|-------------------|-------|---------|-------|--------|
| Оформление заказа | C     | C       | R, U  | C      |
| Просмотр истории  | R     | R       | —     | —      |
| Отмена заказа     | U     | —       | U     | U      |

### 7.26. Данные и бизнес-процессы

Бизнес-процесс показывает движение данных между участниками и системами. На каждом шаге данные преобразуются.

- **Вход процесса** — заявка клиента, платёжное поручение, складская накладная.
- **Шаги процесса** — создаются сущности, меняются статусы, добавляются атрибуты.
- **Выход процесса** — закрытый заказ, подписанный договор, доставленный товар.

### 7.27. Данные и событийная логика системы

Событийная модель: КОГДА событие, ЕСЛИ условие, ТОГДА реакция. Все три части неразрывно связаны с данными.

| Компонент           | Пример                                                                    |
|---------------------|---------------------------------------------------------------------------|
| **КОГДА — событие** | «Статус заказа изменился на Оплачен», «Остаток товара упал ниже минимума» |
| **ЕСЛИ — условие**  | «Сумма заказа больше 100 000», «У клиента есть активные заказы»           |
| **ТОГДА — реакция** | «Перевести заказ в статус Отменён», «Создать Платёж»                      |

> **Без модели данных событийная логика не может быть проверена: непонятно, какие условия возможны и какие реакции допустимы.**

### 7.28. От требования до модели данных

**Пример:** Требование: «Система должна автоматически отменять запись, если пациент не пришёл в течение 30 минут после назначенного времени».

1. **Требование** — автоотмена через 30 мин при неявке пациента.
2. **Сценарий** — система проверяет активные записи; если время истекло — отменяет.
3. **Событийная логика** — КОГДА время + 30 мин, ЕСЛИ статус «Активна» И нет отметки → статус «Неявка» + уведомление.
4. **Модель данных** — Сущность Запись: Статус, Время приёма, Время отметки. Связи с Пациентом и Врачом.

### 7.29. Трассировка данных к требованиям

**Трассировка** — это связывание каждого элемента модели данных с требованием, которое его обосновывает.

> **Трассировка превращает модель данных из «красивой схемы» в обоснованный артефакт, за каждым элементом которого стоит конкретная бизнес-потребность.**

| Ситуация                   | Действие                                                                    |
|----------------------------|-----------------------------------------------------------------------------|
| **Атрибут без требования** | Кандидат на удаление. Зачем хранить данные, которые никто не использует?    |
| **Требование без данных**  | Кандидат на доработку модели. Как реализовать требование без нужных данных? |

### 7.30. Влияние изменений: как одно тянет за собой всё

**Пример:** бизнес меняет правило — «Клиент может отменить заказ только до начала сборки» (раньше было «до отправки»).

Если артефакты не связаны явно — аналитик правит требование и забывает исправить модель данных. Расхождение попадает в код.

### 7.31. Итоги: четыре проекции одной системы

Хороший аналитик видит систему целиком. Требования, сценарии, логика и данные — это не отдельные артефакты, а четыре проекции одного целого.

| Проекция              | Что определяет                                       |
|-----------------------|------------------------------------------------------|
| **Требования**        | Какие данные нужны системе                           |
| **Сценарии**          | Как данные используются на каждом шаге               |
| **Событийная логика** | Как и когда данные изменяются                        |
| **Модель данных**     | Обосновывает каждый атрибут и связь через требования |

> **Инструменты: CRUD-матрица, трассировка данных, проверка модели на сценариях. Явные связи = обоснованность, полнота и управляемость изменений.**

### 7.32. Роль данных в анализе и проверке требований

**Почему данные — центральная тема для аналитика:**
Любая система в своей основе выполняет четыре операции: создать, прочитать, обновить, удалить. Требования описывают поведение системы — но каждое поведение неизбежно оперирует данными. Именно данные являются самым объективным источником информации о том, как система работает на самом деле.

**Три класса проблем, выявляемых через данные:**

| Проблема                   | Пример                                                                                |
|----------------------------|---------------------------------------------------------------------------------------|
| **Проверка реализуемости** | Если данных для выполнения требования не существует в модели — требование невыполнимо |
| **Выявление противоречий** | Два требования по-разному описывают один и тот же атрибут                             |
| **Обнаружение пробелов**   | Сценарий описан, но не указано, откуда система берёт данные                           |

### 7.33. Данные как источник объективной информации

| Интервью и опросы                                                                 | Данные                                                                                                 |
|-----------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| Зависят от памяти и интерпретации. Дают гипотезы — субъективный взгляд участников | Логи системы фиксируют реальное поведение пользователей. Дампы базы данных отражают реальную структуру |

> **Правило: доверяй, но проверяй. Интервью — источник гипотез. Данные — источник фактов.**

### 7.34. Источники данных для аналитика

| Источник                    | Что даёт                                                |
|-----------------------------|---------------------------------------------------------|
| **Система-предшественник**  | База данных, логи, дампы существующего решения          |
| **Документы и регламенты**  | Формы, отчёты, инструкции, бизнес-правила               |
| **Пользовательские данные** | Тикеты поддержки, опросы, записи тестирований           |
| **Внешние источники**       | Отраслевые стандарты, реестры, API смежных систем       |
| **Результаты наблюдения**   | Записи экранов, хронометраж операций, фото рабочих мест |

**Пример из практики:** Анализ логов показывает, что 40% пользователей после оформления заказа сразу переходят в историю заказов. Это неозвученное требование к навигации — выявленное только через данные, а не через интервью.

### 7.35. Документы и регламенты как источник

Документы дают формальную картину того, как организация описывает свои процессы. Сравнение документов с реальными данными вскрывает разрывы между тем, как должно быть, и тем, как есть на самом деле.

| Тип документа       | Что даёт                                                                       |
|---------------------|--------------------------------------------------------------------------------|
| **Формы и шаблоны** | Какие поля существуют, какие обязательны, какие справочники используются       |
| **Отчёты**          | Какие данные агрегируются, в каких разрезах и с какой периодичностью           |
| **Инструкции**      | Пошаговое описание операций: что заполняется, что проверяется                  |
| **Регламенты**      | Бизнес-правила, зафиксированные формально: лимиты, сроки, цепочки согласований |

### 7.36. Пользовательские данные и обратная связь

Пользователи редко могут точно сформулировать требования — но их действия и обращения в поддержку говорят сами за себя.

- **Тикеты поддержки** — частые проблемы, непонятные интерфейсные элементы, запросы на новые функции.
- **Результаты опросов** — субъективное восприятие, агрегированное по большой выборке.
- **Записи тестирований** — где пользователь «спотыкается», какие данные вводит.
- **Анализ обращений** — классификация по типам, частотность, корреляция с версиями.

**Пример сигнала из данных:** 30% обращений в поддержку связаны с проблемой «не могу найти заказ». Это не просто UX-проблема — это сигнал, что данных для поиска недостаточно: отсутствует нужный атрибут или не предусмотрен сценарий фильтрации.

### 7.37. Внешние источники и отраслевые стандарты

- **Отраслевые справочники** — классификаторы, коды, стандартные списки значений.
- **Нормативные требования** — законы о хранении данных, стандарты отчётности.
- **API смежных систем** — какие данные доступны, в каком формате и с какой периодичностью.
- **Открытые данные** — государственные реестры, статистика.

**Пример:** Стандарт PCI DSS прямо запрещает хранить полный номер карты и CVV. Это не пожелание — это обязательное ограничение, которое напрямую влияет на модель данных ещё на этапе анализа.

### 7.38. Как данные связывают все артефакты аналитика

Данные — это кровеносная система проекта. Они пронизывают каждый артефакт и делают их взаимосвязанными.

| Артефакт              | Связь с данными                                                        |
|-----------------------|------------------------------------------------------------------------|
| **Требования**        | «Система показывает историю» → нужна сущность Заказ с атрибутами       |
| **Сценарии**          | Каждый шаг сценария — это CRUD-операция над конкретными сущностями     |
| **Событийная логика** | Условия событий — это проверка атрибутов и связей между сущностями     |
| **Интерфейсы**        | Поля ввода → атрибуты; таблицы → сущности; фильтры → связи             |
| **API**               | JSON-структуры запросов и ответов — это сериализованные бизнес-объекты |

### 7.39. Практический подход: от данных к требованиям и обратно

| Прямой ход                                                                                                                  | Обратный ход                                                                                                                           |
|-----------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| Требования → Модель данных. Читаем требования, выявляем сущности и атрибуты, строим модель. Стартовая точка нового проекта. | Данные → Проверка требований. Смотрим на реальные данные в старой системе, проверяем, все ли сценарии покрыты. Незаменим при миграции. |

> **Этот цикл работает как на старте проекта, так и при доработках существующей системы. Данные — не только результат анализа, но и его главный инструмент.**

### 7.40. Типичные ошибки в работе с данными

1. **Игнорирование данных** — аналитик строит модель только на основе интервью, не заглядывая в реальную базу.
2. **Избыточное доверие данным** — «В старой системе так было — значит, так и надо». Старая система могла содержать ошибки, накопленные годами.
3. **Неиспользование логов** — логи показывают реальное поведение пользователей, но аналитики редко обращаются к ним.
4. **Забытые источники** — аналитик использует только базу данных, игнорируя документы, тикеты поддержки и внешние стандарты.
5. **Отсутствие проверки полноты** — модель построена, но не проверена на реальных сценариях.

### 7.41. Конспект занятия: логическая модель данных (ER-диаграмма)

**Тема занятия:** Построение логической модели данных (ER-диаграммы): выделение сущностей, атрибутов, ключей и связей. Переход от бизнес-объектов к структуре базы данных. Работа с бизнес-правилами, ограничениями и целостностью данных.

**Ключевые понятия:**
- **Логическая модель данных** — описание бизнес-объектов, их атрибутов и связей без привязки к конкретной СУБД.
- **Физическая модель данных** — то, как данные хранятся в конкретной базе данных.
- **Бизнес-объект** — объект реального мира (студент, курс, заказ), который имеет атрибуты, поведение и жизненный цикл.
- **Сущность** — более технический термин, ближе к таблице.
- **Атрибут** — характеристика сущности.
- **Первичный ключ (PK)** — уникальный идентификатор строки в таблице.
- **Внешний ключ (FK)** — ссылка на первичный ключ другой таблицы.
- **Связочная (ассоциативная) таблица** — таблица, которая связывает две другие таблицы при связи «многие ко многим».
- **Бизнес-правило** — ограничение или условие, которое влияет на работу системы, но не является требованием.
- **Нормализация** — разбивка данных по таблицам, чтобы избежать дублирования.
- **Индекс** — дополнительная структура для быстрого поиска по полю.
- **Каскадное удаление** — при удалении записи из основной таблицы автоматически удаляются связанные записи.
- **Транзакция** — последовательность действий с базой данных, которая воспринимается как единое целое.
- **ACID** — свойства транзакции: атомарность, согласованность, изолированность, долговечность.

**Как обеспечить целостность данных:**
- **Not null** — поле обязательно для заполнения.
- **Unique** — значения не повторяются (email).
- **Check** — диапазон значений (оценка 0–100).
- **Каскадное удаление** — удаление связанных записей (аккуратно!).
- **Транзакции** — либо всё, либо ничего.

**Пример 1: Кейс онлайн-школы**

Кандидаты в сущности:
- Студент — ID, ФИО, email, телефон, часовой пояс.
- Курс (программа) — ID, название, продолжительность, сложность.
- Преподаватель — ID, ФИО, специализация, контакты, режим работы.
- Куратор — можно объединить с преподавателем в «Сотрудник».
- Модуль — ID, название, порядковый номер, описание, ID курса (FK).
- Домашнее задание — ID, название, условия, проходной балл, количество попыток.
- Обучение — связочная таблица: ID студента (FK), ID программы (FK), дата старта, статус.
- Личный кабинет — можно не выделять, а сделать атрибутом студента.

Лишние: каталог курсов, рейтинг курса, запись.

Связи:
- Студент ↔ Программа: многие ко многим → таблица «Обучение».
- Программа → Модуль: один ко многим.
- Модуль → Домашнее задание: один ко многим.
- Преподаватель ↔ Модуль: многие ко многим → связочная таблица.

**Пример 2: Бизнес-правила**
- «Нельзя зарегистрироваться на один email дважды» → unique constraint на поле email.
- «Оценка от 0 до 100» → check constraint.
- «Доступ к следующему модулю только после прохождения предыдущего» → бизнес-правило, влияет на логику доступа.
- «После отчисления доступ закрывается» → правило для статуса.
- «Курс от 4 до 8 модулей» → check constraint или правило валидации.

**Пример 3: Индексы**
- Если часто ищем курс по ID → индекс на поле ID.
- Если часто ищем студента по email → индекс на email.
- Плюс: быстрый поиск. Минус: медленная запись, дополнительное место.

**Нюансы:**
- Аналитик работает и с логической, и с физической моделью. Начинаем с логической, но спускаемся до физической.
- С заказчиком говорим на языке бизнес-объектов. С разработчиком — на языке таблиц и ключей.
- Связочная таблица может быть бизнесовой или технической.
- Индексы — палка о двух концах.
- Транзакции — это всегда так работает. Не прописываем в требованиях, но знаем.

### 7.42. Конспект занятия: работа с данными — маппинг, CRUD-матрица

**Тема занятия:** Фронтальная работа в формате мастер-класс «Проверка согласованности требований, сценариев и логики системы».

**Ключевые понятия:**
- **Маппинг данных** — сопоставление полей из одного источника (например, API-запроса) с полями в базе данных.
- **CRUD-матрица** — таблица, которая показывает, какие операции (Create, Read, Update, Delete) выполняются над каждой сущностью в рамках конкретного процесса.
- **CRUD** — аббревиатура основных операций над данными: C (Create) — создание, R (Read) — чтение, U (Update) — обновление, D (Delete) — удаление.
- **Бизнес-правило vs Требование** — требование описывает, что система должна делать. Бизнес-правило — это ограничение или условие, которое влияет на работу, но не является требованием к системе напрямую.
- **ENUM** — тип данных, который может принимать только заранее заданные значения.
- **Унификация наименований** — использование одинаковых названий для одинаковых по смыслу полей в разных таблицах (например, created_at везде).
- **Запись с точкой (таблица.атрибут)** — способ указать, к какой таблице относится поле.
- **Трассировка требований** — связывание требований с данными, тест-кейсами, сценариями и другими артефактами.

**Как проверить, хватает ли данных для требования:**
1. Прочитай требование — что нужно сделать.
2. Найди сущность — к какой таблице относится.
3. Проверь атрибуты — есть ли нужные поля.
4. Если данных не хватает — что нужно добавить.
5. Если данных хватает — укажи, из какого поля берётся значение.

**Как составить маппинг:**
1. Возьми тело запроса (что приходит от API).
2. Определи, какие данные нужны для сохранения.
3. Найди соответствующие поля в базе данных.
4. Запиши соответствие: поле_API → таблица.атрибут.
5. Если поля нет — отметь, что нужно добавить.
6. Если поле есть, но не подходит по типу — отметь, что сохранить нельзя.

**Как заполнять CRUD-матрицу:**
1. Определи процессы.
2. Определи сущности.
3. Для каждого процесса определи, какие операции выполняются над каждой сущностью.
4. Если сущность не участвует — ставь прочерк.

**Как отличить требование от бизнес-правила:**
- Требование: «Система должна начислять кэшбэк за покупки».
- Бизнес-правило: «Кэшбэк не начисляется на заказы дешевле 500 рублей».

**Пример: Маппинг данных из API**

Запрос API (POST):
- order_id → order.id
- customer_email → client.email
- total_amount → order.total_amount
- items → order_item.*
  - item_id → order_item.id
  - category → order_item.category
  - price → order_item.price
- payment_status → проблема: в базе есть order.status с ENUM («оформлен», «оплачен», «отменён»), но нет значения «paid».
- payment_date → проблема: в базе есть order.created_at, но это дата создания, а не оплаты.

**Вывод:** данных не хватает. Нужно добавить поле payment_date, а также проверить, можно ли сохранить статус «paid» в существующий ENUM.

**Пример: CRUD-матрица для процесса «Оформление и оплата заказа»**

| Сущность           | C | R | U | D |
|--------------------|---|---|---|---|
| Клиент             | — | R | — | — |
| Заказ              | C | R | U | — |
| Позиция заказа     | C | R | — | — |
| Транзакция кэшбэка | C | — | — | — |

**Пояснение:**
- Клиент: только читаем.
- Заказ: создаём, читаем, обновляем.
- Позиция заказа: создаём, читаем.
- Транзакция кэшбэка: создаём.

**Ошибки в требованиях (кейс Cashback Pro):**
1. Требования сформулированы как бизнес-правила.
2. В модели данных не хватает данных.
3. Статус оплаты не сохраняется.

**Нюансы:**
- Маппинг — частая задача аналитика.
- CRUD-матрица — опциональный артефакт, но полезный.
- Нормализация — тема следующего занятия.
- Индексы — ускоряют поиск, замедляют запись.

## 8. Бизнес-процессы как объект анализа

### 8.1. Почему аналитик должен понимать бизнес-процессы

- **Автоматизация — не хаоса, а процесса.** Прежде чем автоматизировать — нужно понять, что именно автоматизируешь.
- **Требования без процесса оторваны от реальности.** Описывают «удобный интерфейс» вместо решения реальной проблемы.
- **Процесс — каркас для сценариев и требований.** Пользовательские сценарии и функциональные требования нанизываются на структуру процесса.

### 8.2. Что такое бизнес-процесс

**Бизнес-процесс** — это устойчивая, целенаправленная последовательность действий, преобразующая входы в выходы, представляющие ценность для потребителя.

**Пример:** «Приём заказа» — на входе обращение клиента, на выходе созданный и подтверждённый заказ.

**Свойства:**
- **Устойчивая** — выполняется регулярно.
- **Целенаправленная** — есть измеримый результат.
- **Преобразующая** — вход → другой выход.

### 8.3. Зачем аналитику моделировать бизнес-процесс

| Цель                               | Что даёт                                                       |
|------------------------------------|----------------------------------------------------------------|
| **Увидеть полную картину**         | Не отдельную функцию, а сквозной поток от начала до конца      |
| **Найти узкие места**              | Дублирование, лишние шаги, ручной труд                         |
| **Выявить роли и ответственность** | Определить, кто реально участвует в процессе и за что отвечает |
| **Согласовать понимание**          | Схема процесса — единый язык для бизнеса и команды разработки  |

### 8.4. Границы бизнес-процесса

| Граница                    | Что определяет                                             |
|----------------------------|------------------------------------------------------------|
| **Верхняя граница: Вход**  | Событие или ресурс, запускающий процесс (звонок, заявка)   |
| **Нижняя граница: Выход**  | Ценный результат (заказ доставлен, договор подписан)       |
| **Горизонтальные границы** | Взаимодействие со смежными процессами и внешними системами |

> **Правило:** определяйте границы до начала детального моделирования. Иначе процесс «расползается» и анализ теряет фокус.

### 8.5. Основные элементы бизнес-процесса

1. **Событие** — то, что происходит и влияет на поток: стартовое, промежуточное, конечное.
2. **Действие** — единица работы, выполняемая участником или системой.
3. **Участник** — роль или система, выполняющая действие.
4. **Поток и развилка** — стрелки перехода и точки ветвления потока управления.
5. **Данные** — документы, сообщения и записи, передаваемые между шагами.

### 8.6. События: стартовые, промежуточные, конечные

| Тип события       | Описание                                           | Пример                                                |
|-------------------|----------------------------------------------------|-------------------------------------------------------|
| **Стартовое**     | Всегда одно на процесс. Запускает поток            | «Клиент оформил заявку»                               |
| **Промежуточное** | Происходит в ходе процесса, может изменить его ход | «Таймер истёк»                                        |
| **Конечное**      | Может быть несколько                               | «Заказ выполнен», «Заказ отменён», «Клиент отказался» |

> **Событие — это свершившийся факт, а не работа. Действие — это работа, которая выполняется.**

### 8.7. Действия и их декомпозиция

**Правила хорошего действия:**
Действие выполняется одним участником, в одном месте, в один момент времени.

**Декомпозиция действий:**
Действие может раскрываться в подпроцесс — отдельную детальную схему внутри.

> **Плохо:** «Оформить и согласовать заказ» — два действия, два участника смешаны в одном шаге.
> **Хорошо:** «Менеджер оформляет заказ» → «Руководитель согласует заказ».

| Для обзора                     | Для автоматизации                     |
|--------------------------------|---------------------------------------|
| Крупные блоки, без детализации | Максимальная детализация каждого шага |

### 8.8. Участники процесса: роли и системы

- **Роль ≠ Должность.** Роль — это функция в процессе: «Инициатор», «Согласующий», «Исполнитель». Одна должность может выполнять несколько ролей.
- **Дорожки на схеме.** Визуально разделяют зоны ответственности. Каждый участник — своя дорожка (swim lane).
- **Система — тоже участник.** Если система выполняет действие автоматически — она участник. «CRM отправляет уведомление», «Платёжный шлюз обрабатывает платёж».

### 8.9. Ветвления и развилки

| Тип                       | Описание                                            | Пример                                                           |
|---------------------------|-----------------------------------------------------|------------------------------------------------------------------|
| **XOR — Исключающее ИЛИ** | Выбирается только один путь из нескольких доступных | Если сумма меньше 100 тыс — согласование не нужно, иначе — нужно |
| **AND — Параллельное И**  | Запускаются все пути одновременно                   | Отправить уведомление клиенту и одновременно начать сборку       |
| **Условный переход**      | Путь выбирается по определённому условию            | —                                                                |

> **После развилки должно быть слияние, если пути не ведут к разным конечным событиям.**
> **Развилки — источник альтернативных и исключительных сценариев в Use Case. Каждая ветка — отдельный сценарий в требованиях.**

### 8.10. Бизнес-процесс и требования: как связаны

| Элемент процесса        | Требование                                            |
|-------------------------|-------------------------------------------------------|
| **Шаг процесса**        | → Функциональное требование к автоматизации           |
| **Ветвление**           | → Альтернативный или исключительный сценарий Use Case |
| **Участник**            | → Пользовательская роль в системе                     |
| **Передаваемые данные** | → Атрибут сущности или параметр API                   |

> **Вывод: не пишите требования, пока не смоделировали процесс. Процесс даёт структуру и обоснование для каждого требования.**

### 8.11. Итоги по бизнес-процессам

1. **Бизнес-процесс — устойчивая последовательность** — преобразует входы в ценный выход. Не разовая задача — регулярная практика.
2. **Границы определяют до моделирования** — вход, выход, смежные системы.
3. **Моделирование — способ увидеть систему целиком** — находите проблемы, обосновывайте требования, согласовывайте понимание.
4. **Хороший аналитик начинает с процесса** — не с кнопок и полей, а с понимания процесса, который они должны поддерживать.

## 9. Интеграции и взаимодействие с внешним окружением

### 9.1. Синхронно и асинхронно

|                                | Синхронно (например, REST API)          | Асинхронно                                                |
|--------------------------------|-----------------------------------------|-----------------------------------------------------------|
| **Принцип**                    | Система отправляет запрос и ждёт ответа | Система сообщает о произошедшем факте и продолжает работу |
| **Если получатель недоступен** | Отправитель получает ошибку             | Получатели читают сообщение сами, в своём темпе           |

### 9.2. Что такое REST

**REST (Representational State Transfer)** — архитектурный стиль построения API, предложенный Роем Филдингом в 2000 году. Это не протокол и не жёсткий стандарт, а набор договорённостей о том, как удобно организовать взаимодействие клиента и сервера поверх HTTP.

**Принципы REST:**
- **Ресурсно-ориентированный подход** — всё, с чем работает API, это ресурс со своим адресом (URL).
- **Клиент-сервер** — клиентская и серверная части разделены и развиваются независимо.
- **Stateless** — каждый запрос самодостаточен, сервер не хранит историю разговора между запросами.
- **Единообразный интерфейс** — одни и те же HTTP-методы означают одно и то же для любого ресурса.

### 9.3. HTTP-методы

| Метод      | Для чего                                          | Пример                   |
|------------|---------------------------------------------------|--------------------------|
| **GET**    | Получить данные                                   | GET /products?id=5521    |
| **POST**   | Создать новый ресурс                              | POST /products           |
| **PUT**    | Полностью заменить ресурс (все поля)              | PUT /products?id=5521    |
| **PATCH**  | Частично обновить ресурс (только изменённые поля) | PATCH /products?id=5521  |
| **DELETE** | Удалить ресурс                                    | DELETE /products?id=5521 |

### 9.4. Идемпотентность

**Идемпотентный метод** — повторный вызов с теми же данными даёт тот же результат, что и один вызов.

- Повторное удаление уже удалённого ресурса безопасно — результат тот же.
- А вот повторный POST с одними и теми же данными создаст два ресурса вместо одного — это не идемпотентно.

### 9.5. Из чего состоит запрос

| Элемент                       | Описание                                                                         | Пример                                  |
|-------------------------------|----------------------------------------------------------------------------------|-----------------------------------------|
| **Параметры пути (path)**     | Часть URL, указывающая на конкретный ресурс                                      | /payments/42 означает «платёж номер 42» |
| **Параметры запроса (query)** | Необязательные уточнения после знака вопроса                                     | /orders?status=paid                     |
| **Заголовки (headers)**       | Служебная информация: Authorization, Content-Type, X-Request-Id, Idempotency-Key | —                                       |
| **Тело запроса**              | Данные, которые передаёт клиент; есть только у POST, PUT, PATCH                  | —                                       |
| **Тело ответа**               | Данные, которые возвращает сервер, вместе с кодом ответа                         | —                                       |

### 9.6. Коды ответов HTTP

**2xx — успех:**
- **200 OK** — успешный GET или PATCH.
- **201 Created** — успешно создан новый ресурс (POST).
- **204 No Content** — успешное действие без тела ответа (обычно DELETE).

**4xx — ошибка на стороне клиента:**
- **400 Bad Request** — некорректные данные в запросе.
- **401 Unauthorized** — не авторизован.
- **403 Forbidden** — авторизован, но нет прав на это действие.
- **404 Not Found** — ресурс не найден.
- **409 Conflict** — конфликт состояния.
- **422 Unprocessable Entity** — данные корректны по формату, но не проходят бизнес-проверку.

**5xx — ошибка на стороне сервера:**
- **500 Internal Server Error** — непредвиденная ошибка сервера.
- **502 Bad Gateway** — сервер получил невалидный ответ от вышестоящего сервера.
- **503 Service Unavailable** — сервис временно недоступен.

### 9.7. Когда система не отвечает

Коды 4xx и 5xx — это тоже ответ, пусть и с ошибкой. Но частый случай при работе с внешними системами — система вообще не отвечает за разумное время. Возникает вопрос таймаутов. Уточняем — сколько ждать ответа и что делать дальше — повторить запрос, показать ошибку или отложить операцию.

### 9.8. Документирование API

- **OpenAPI** — стандарт описания REST API: список эндпоинтов, методов, параметров и форматов данных в машиночитаемом виде.
- **Swagger** — инструмент, который читает такую спецификацию и превращает её в интерактивную документацию, где можно сразу посмотреть и попробовать каждый запрос.

### 9.9. PUT vs PATCH

- **PUT** — полная замена данных: PUT /products/{id}, нужно передать все поля целиком.
- **PATCH** — частичное обновление: PATCH /products/{id}, например, только остаток на складе.
- Если поле не передано в PUT — оно затрётся пустым значением.

### 9.10. GraphQL

- В REST под каждый ресурс — свой эндпоинт, и в ответ приходит весь объект целиком.
- В GraphQL — один эндпоинт, а клиент сам описывает в запросе, какие поля ему нужны.
- Пример: вместо GET /products/42 с полным объектом — запрос вида `{ product(id: 42) { name price } }` с ровно двумя полями в ответе.

### 9.11. Вебхуки и файловый обмен

- **Вебхук** — внешняя система сама уведомляет вас о событии HTTP-запросом на ваш адрес, как только это произошло.
- **Файловый обмен** — системы обмениваются данными через файлы (например, выгрузка раз в сутки), а не через прямые вызовы.
- Также существуют SOAP, gRPC, WebSocket и другие.

### 9.12. Что ещё учитывать при интеграциях

- **Белые списки (whitelist)** — к API или брокеру могут обращаться только заранее известные системы.
- **Ограничение частоты запросов (rate limiting)** — контроль нагрузки, чтобы один партнёр не мог перегрузить систему.
- **Клиентские сертификаты** — для Kafka и похожих систем доступ часто подтверждается сертификатом, а не токеном.
- **Версионирование API (/v1/, /v2/)** — чтобы развивать контракт, не ломая уже работающих партнёров.
- **Защита от каскадных сбоев (circuit breaker)** — если внешняя система стабильно не отвечает, стоит временно перестать её дёргать.

### 9.13. Частые ошибки при проектировании REST API

1. Неверный выбор HTTP-метода под операцию (например, GET, который на самом деле что-то меняет).
2. Ресурс проектируется раньше модели данных, а не наоборот.
3. Отсутствие версионирования API — при изменении контракта ломаются уже работающие клиенты.
4. Разный формат ошибок для разных методов — у каждой ошибки должен быть предсказуемый, единый формат.
5. Непоследовательное именование ресурсов (иногда /product, иногда /products).

### 9.14. Kafka: основные понятия

| Понятие                     | Описание                                                                                                                                                        |
|-----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Kafka**                   | Брокер сообщений: принимает сообщения от одних систем и хранит их для других. Сообщение после прочтения не удаляется, его могут прочитать несколько получателей |
| **Топик**                   | Канал для событий одного вида                                                                                                                                   |
| **Партиция**                | Часть топика. Внутри партиции сообщения хранятся строго по порядку                                                                                              |
| **Оффсет**                  | Номер сообщения в партиции, «закладка», до которой дочитал получатель                                                                                           |
| **Продюсер**                | Система, которая пишет события в топик                                                                                                                          |
| **Консюмер**                | Система, которая читает события из топика                                                                                                                       |
| **Ключ сообщения**          | События с одинаковым ключом попадают в одну партицию и обрабатываются по порядку                                                                                |
| **Событие**                 | Факт о прошлом, название в прошедшем времени: «Пакет куплен»                                                                                                    |
| **Retention**               | Срок хранения сообщений в Kafka. Стандарт: 4 часа или сутки. Чем дольше — тем дороже                                                                            |
| **Лаг Kafka**               | Количество сообщений, которые накопились и ещё не вычитаны. Растущий лаг — проблема                                                                             |
| **Dead Letter Queue (DLQ)** | Очередь для сообщений, которые не удалось отправить в Kafka                                                                                                     |

### 9.15. Дубликаты и ошибки в Kafka

Обычно Kafka гарантирует доставку «как минимум один раз»: сообщение не потеряется, но может прийти повторно. Поэтому получатель должен обрабатывать повтор так, чтобы результат не менялся (идемпотентная обработка), например хранить идентификаторы уже обработанных событий.

Если сообщение не удаётся обработать, делают несколько повторов, а затем перекладывают его в отдельный топик DLQ (очередь неразобранных сообщений) для ручного разбора.

### 9.16. Как выбрать: API или событие через Kafka

| Критерий                                      | Скорее синхронный API                       | Скорее событие через Kafka                           |
|-----------------------------------------------|---------------------------------------------|------------------------------------------------------|
| **Нужен ли ответ, чтобы продолжить действие** | Да, пользователь ждёт результата            | Нет, достаточно знать, что факт зафиксирован         |
| **Сколько получателей**                       | Один                                        | Несколько, и их число может расти                    |
| **Что если получатель недоступен**            | Действие должно не состояться               | Действие должно состояться, получатель догонит позже |
| **Требования к согласованности**              | Проверка и изменение должны быть атомарными | Допустима задержка в секунды и минуты                |

### 9.17. Гарантии доставки

| Стратегия                                | Описание                                                               | Риск                                         |
|------------------------------------------|------------------------------------------------------------------------|----------------------------------------------|
| **Сначала подтвердить, потом сохранить** | Аналогия с газетным киоском: сначала расписаться, потом забрать газету | Риск потери                                  |
| **Сначала сохранить, потом подтвердить** | Надёжнее, но медленнее                                                 | Нужен компенсационный механизм против дублей |
| **Одновременно**                         | Только внутри Kafka                                                    | —                                            |

### 9.18. Как оформлять документацию по Kafka

1. Название события и топика (английские буквы, цифры, подчёркивания, точка, версия).
2. Описание топика (опционально).
3. Продюсер: кто публикует.
4. Момент публикации: триггер (открылся договор, изменился статус).
5. Ключ сообщения (если нужен порядок).
6. Гарантия доставки: стратегия подтверждения.
7. Retention: срок хранения.
8. Формат и схема: заголовки, тело сообщения, типы данных, обязательность, примеры.
9. Версия схемы: v1, v2 и дата.
10. Связанные требования (опционально).
11. Хосты и IP-адреса для подключения (отдельно для каждого контура: тест, ПСИ, ПРО).
12. Обработка дубликатов: по версии, времени изменения, полю.
13. Мониторинг: лаг, количество ошибок, скорость вычитки.

### 9.19. Headers и body

У сообщения две части: headers и body.

- **Headers** — служебная информация: eventId, eventType, timestamp, source и так далее.
- **Body** — бизнес-данные, специфичные для этого события.

### 9.20. Схема события (валидационная схема)

JSON-документ с описанием атрибутов, типов, обязательности. Используется для проверки сообщений.

**Для каждого поля:** название, тип, обязательность, пример, min/max.

**Версия схемы (v1, v2)** с датой. **Валидационная схема:** проверять или не проверять сообщения по схеме.

### 9.21. ADR (Architecture Decision Record)

**ADR** — запись архитектурного решения: какое решение принято, почему, какие альтернативы рассматривались, кто утвердил. Нужна, чтобы через год не возникал вопрос «а почему мы так сделали?».

**Как оформлять ADR:**
1. Контекст: в каких условиях принимается решение.
2. Варианты: какие альтернативы рассматривались.
3. Решение: что выбрано.
4. Последствия: что выполняется, что не выполняется, плюсы и минусы.
5. Кто утвердил: архитектор, лидер разработки, безопасность и т.д.

> **ADR — не для каждого решения: только для крупных, верхнеуровневых. Изменение названия атрибута — не ADR.**

### 9.22. Мониторинг Kafka

- **Лаг** — отставание потребителя от продюсера. Маленький лаг — нормально, растущий — проблема.
- **Количество ошибок** — сколько сообщений не удалось обработать.
- **Скорость вычитки** — как быстро потребитель обрабатывает сообщения.
- **Мониторинг лага** реализуется на стороне Kafka, не на консюмере.

### 9.23. Типичные ошибки и нюансы интеграций

- Нет плохих или хороших способов интеграции — всё зависит от контекста и условий.
- Kafka не подходит для бронирования — нужен синхронный ответ, а Kafka асинхронна.
- API не подходит для массовой рассылки событий многим потребителям.
- Retention: чем дольше хранить сообщения, тем дороже.
- Лаг: маленький и колеблющийся — нормально. Растущий — проблема.
- Гарантия доставки: сначала подтвердить, потом сохранить — риск потери. Сначала сохранить, потом подтвердить — надёжнее, но медленнее.
- Дубликаты: без обработки можно задвоить данные.
- Схема события: обязательно указывать тип, обязательность, пример, min/max.
- Хосты для подключения: разные для теста, ПСИ, ПРО.
- Redis — не брокер сообщений, но можно использовать как легковесный брокер. Не хранит данные как Kafka, нет retention.
- Консюмер-группа: название должно быть уникальным для конкретной Kafka.
- Тело сообщения: не нужно класть все данные, которые есть. Нужно спросить потребителей, что им нужно.
- Настройка Kafka — не задача аналитика. Аналитик определяет состав события, схему, маппинг.
- Партиции: количество лучше согласовать с разработчиком.
- Не нужно сохранять все данные из сообщения. Можно выбрать 40 полей из 50.

### 9.24. Кейс: каталог товаров ДомСад

Домен ДомСад, сущность «Товар» в каталоге. Пять операций по одной, каждая — готовый кусочек YAML, который можно скопировать и вставить целиком в редактор, чтобы сразу увидеть, как это выглядит и почитать сгенерированную документацию.

**1. Создание товара**

Подсказка: у POST есть тело запроса и заголовок Idempotency-Key — он нужен, потому что POST сам по себе не идемпотентен, и повторная отправка без этого заголовка создала бы вторую карточку товара.

```yaml
openapi: 3.0.3
info:
  title: ДомСад - Каталог товаров API
  version: 1.0.0
paths:
  /products:
    post:
      summary: Создать товар
      parameters:
        - name: Authorization
          in: header
          required: true
          schema:
            type: string
            example: "Bearer eyJhbGciOi..."
        - name: Date
          in: header
          required: true
          schema:
            type: string
            format: date-time
            example: "2026-09-18T11:47:00Z"
        - name: X-Request-Id
          in: header
          required: true
          schema:
            type: string
            example: "req-33a9f1"
        - name: Idempotency-Key
          in: header
          required: true
          schema:
            type: string
            example: "b3f1c2e4-9a7d-4b6e-8f2a-1d5e6c7b8a90"
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [name, category, sku]
              properties:
                name:
                  type: string
                  example: "Лейка садовая 5л"
                category:
                  type: string
                  example: "Инвентарь для полива"
                sku:
                  type: string
                  example: "DS-10234"
                description:
                  type: string
                  example: "Пластиковая лейка с рассекателем"
                stock:
                  type: integer
                  example: 120
      responses:
        '201':
          description: Товар создан
          content:
            application/json:
              schema:
                type: object
                properties:
                  productId:
                    type: string
                    example: "prod-5521"
                  name:
                    type: string
                    example: "Лейка садовая 5л"
                  status:
                    type: string
                    example: "active"
        '400':
          description: Некорректные данные запроса
```

### 9.25. Регистрация на вебинар: сценарии использования системы

**Рекомендации по написанию Use Case:**

**Как искать альтернативные сценарии** — альтернативы почти всегда прячутся в одном из этих мест:
- Разные способы сделать то же самое действие.
- Разные способы оплаты/подтверждения.
- Скидки и специальные условия.
- Разные роли, идущие к одной цели по-разному.
- Уже сохранённые/предзаполненные данные.
- Отложенное или частичное выполнение.

Обычно находятся через вопрос: «Есть ли другой путь к этой же цели, который тоже не является ошибкой?»

**Как искать исключительные сценарии:**
- Данные некорректны или отсутствуют.
- Внешняя система недоступна или ответила с ошибкой.
- Ресурс закончился или недоступен.
- Права/авторизация не пройдены.
- Гонка состояний (два пользователя делают одно и то же почти одновременно).
- Действие уже было выполнено раньше.
- Пользователь передумал или прервал процесс.
- Технический сбой на стороне системы.

Обычно находятся через вопрос: «Что должно быть истинно, чтобы этот шаг вообще случился — и что если это условие не выполнено?»

**Общий приём:** пройтись по каждому шагу основного потока и для каждого явно спросить — может ли пользователь сделать это иначе (альтернатива), может ли этот шаг провалиться (исключение).

**Use Case: Регистрация пользователя на вебинар**

Актор: Посетитель сайта
Предусловие: вебинар опубликован и открыт для регистрации

1. Пользователь открывает страницу вебинара.
2. Пользователь вводит email, имя и при наличии — промокод.
3. Пользователь нажимает «Зарегистрироваться».
4. Система проверяет, что этот email ранее не регистрировался на этот вебинар.
5. Система проверяет наличие свободных мест.
6. Система создаёт запись о регистрации.
7. Система отправляет письмо с подтверждением и ссылкой на подключение.

Постусловие: пользователь зарегистрирован, запись создана, письмо отправлено.

**Альтернативный поток А1 (от шага 5) — регистрация по промокоду:**
5a. Если свободных мест нет, то система проверяет, был ли введён промокод.
5b. Если да — система проверяет наличие приоритетных мест по нему.
5c. Если приоритетные места есть — система регистрирует пользователя вне общего лимита, переход к шагу 6.

**Альтернативный поток А2 (от шага 5) — лист ожидания:**
5a. Обычных мест нет, но пользователь соглашается встать в лист ожидания.
5b. Система создаёт запись в листе ожидания, переход к шагу 7 с изменённым текстом письма.

**Альтернативный поток А3 (от шага 2) — быстрая регистрация через соцсеть:**
2a. Пользователь нажимает «Войти через VK/Google» вместо ручного ввода email и имени.
2b. Система получает email и имя из профиля соцсети, переход к шагу 4.

**Исключительный поток И1 (от шага 5) — места закончились:**
5x. Мест нет, пользователь отказывается от листа ожидания — система показывает сообщение «мест нет».
Постусловие: регистрация не создана, пользователю показано сообщение об отсутствии мест.

**Исключительный поток И2 (от шага 4) — email уже зарегистрирован:**
4x. Система показывает сообщение «вы уже зарегистрированы».
Постусловие: повторная запись не создана, пользователь направлен к уже существующему подтверждению.

**Исключительный поток И3 (от шага 2) — некорректный формат email:**
2x. Введённый email не соответствует формату (нет «@», лишние пробелы и так далее) — система показывает ошибку валидации прямо в поле, не позволяя перейти к следующему шагу.
Постусловие: регистрация не начата, пользователь возвращён к исправлению поля email.

## 10. Документация аналитика: виды, структура, упаковка

### 10.1. Зачем аналитику документация

- Устные договорённости забываются — документы остаются.
- **Фиксируют решения** — договорённости становятся фактом.
- **Синхронизируют команду** — единое понимание у всех участников.
- **Передают знания** — онбординг, поддержка, развитие.
- **Защищают от споров** — «Мы договаривались не так» — больше не аргумент.

### 10.2. Два типа документации

| Аналитическая                         | Проектная                        |
|---------------------------------------|----------------------------------|
| Отвечает на вопросы «зачем?» и «что?» | Отвечает на вопрос «как именно?» |
| Для принятия решений бизнесом         | Для реализации командой          |
| Фиксирует результаты обследования     | Детальные спецификации           |
| Появляется на ранних этапах           | Появляется ближе к разработке    |

> **Граница условна: один документ может содержать элементы обоих типов. Документация развивается от общих концепций к детальным спецификациям.**

### 10.3. Концептуальная записка (Vision)

Фиксирует образ будущей системы до начала сбора требований.

**Содержит:**
- Проблема и бизнес-цели.
- Ключевые стейкхолдеры.
- Верхнеуровневые границы.
- Основные риски.

**Формат:** 3–5 страниц · читается за 15 минут · у всех одинаковое понимание цели.

### 10.4. Реестр заинтересованных сторон (Stakeholder Register)

Кто влияет на проект и на кого влияет проект.

| Раздел                     | Содержание                       |
|----------------------------|----------------------------------|
| **Список стейкхолдеров**   | Роли, уровень влияния и интереса |
| **Потребности и ожидания** | Что важно для каждой группы      |
| **Коммуникация**           | Предпочтительный канал и частота |

**Матрица влияния/интереса:**
- **Управлять плотно** — высокое влияние, высокий интерес.
- **Поддерживать удовлетворённость** — высокое влияние, низкий интерес.
- **Держать в курсе** — низкое влияние, высокий интерес.
- **Мониторить** — низкое влияние, низкий интерес.

### 10.5. Документы по результатам обследования

- **Протоколы встреч** — дата, участники, тезисы, решения, открытые вопросы.
- **Отчёт об обследовании (As-Is → To-Be)** — текущая ситуация, проблемы, потребности, предложения по улучшению.

> **Отчёт об обследовании — мост между сбором информации и началом проектирования.**

### 10.6. Реестр требований и бэклог продукта

| Реестр требований                                | Бэклог продукта                                                      |
|--------------------------------------------------|----------------------------------------------------------------------|
| Полный список всех требований с атрибутами       | Приоритизированный список задач для команды                          |
| ID, Описание, Источник, Приоритет, Статус, Тесты | User Story, Acceptance Criteria, Story Points, Sprint, Статус, Связи |
| Confluence / Excel — каскадная модель            | Jira / трекер — Agile-методология                                    |

### 10.7. SRS — Спецификация требований

**Software Requirements Specification** — документ перед началом активной разработки.

> **SRS — это контракт. Под ним подписываются заказчик и команда.**

**Состав:**
1. Функциональные требования — Use Cases / User Stories.
2. Нефункциональные требования — производительность, безопасность, надёжность.
3. Модели данных, интеграции — ER-диаграммы, интерфейсы, ограничения.

### 10.8. Модели и диаграммы

Визуальный язык аналитика — одна схема заменяет страницы текста.

| Диаграмма                        | Что показывает                                   | Когда использовать                        |
|----------------------------------|--------------------------------------------------|-------------------------------------------|
| **ERD (сущность-связь)**         | Сущности, атрибуты, связи между данными          | Проектирование БД, доменная модель        |
| **Sequence (UML)**               | Обмен сообщениями между участниками во времени   | Конкретный сценарий взаимодействия        |
| **BPMN (бизнес-процесс)**        | Поток процесса: события, шаги, развилки, роли    | Описание процесса «как есть / как будет»  |
| **Use Case (UML)**               | Кто и что делает в системе, на высоком уровне    | Ранний сбор требований, границы системы   |
| **Activity (UML)**               | Похожа на BPMN, но проще, ближе к алгоритму      | Поток шагов без привязки к ролям          |
| **Component / Deployment (UML)** | Из каких технических компонентов состоит система | Архитектурные обсуждения с разработчиками |
| **State Diagram**                | Жизненный цикл сущности: состояния и переходы    | Моделирование жизненного цикла            |
| **Контекстная диаграмма**        | Система, окружение, границы и потоки данных      | Определение границ системы                |

### 10.9. Техническое задание (ТЗ)

**ГОСТ 34.602-89** — стандарт для ТЗ.

**Состав:**
1. Общие сведения и назначение системы.
2. Требования к функциям и видам обеспечения.
3. Состав работ и порядок приёмки.

**Применение:**
- Используется в каскадной модели и при работе с внешними подрядчиками.
- **Частное ТЗ (ЧТЗ)** — ТЗ на отдельную подсистему или модуль.
- **В Agile-проектах** ТЗ заменяется набором User Stories с Acceptance Criteria и сопровождающими моделями.

> **Формат документа зависит от методологии и контракта с заказчиком.**

### 10.10. Документация этапа проектирования

Мост между аналитическими артефактами и кодом.

- **Описание API (Swagger / OpenAPI)** — эндпоинты, методы, параметры, форматы, коды ошибок.
- **Техническая спецификация модуля** — детальная логика модуля для разработчиков.
- **Маппинг данных** — правила преобразования между системами, форматы обмена.
- **Инструкция по развёртыванию** — окружение, зависимости, порядок установки и настройки.

### 10.11. Эксплуатационная документация

| Документ                     | Содержание                            |
|------------------------------|---------------------------------------|
| **Руководство пользователя** | Функции системы на языке пользователя |
| **Обучающие материалы**      | Презентации, видео, тренинги          |
| **База знаний и FAQ**        | Типовые проблемы и их решения         |

> **Аналитик — лучший рецензент этих документов: он лучше всех знает логику системы.**

### 10.12. Итоги по документации

Документация развивается от общих концепций к детальным спецификациям — на каждом этапе свой набор артефактов:

1. **Инициация** — Vision, реестр стейкхолдеров.
2. **Обследование** — протоколы, отчёт, реестр требований.
3. **Проектирование** — SRS, модели, ТЗ, API.
4. **Эксплуатация** — руководства, FAQ.

> **Хороший документ — тот, который читают и используют. Не тот, который толстый и пылится в Confluence.**

### 10.13. Принципы структурирования комплекта аналитических материалов

**Зачем структурировать и упаковывать артефакты:**
Аналитик создаёт десятки артефактов: требования, модели, диаграммы, протоколы, спецификации. Без структуры — это хаос, в котором команда не может ориентироваться. Структурирование превращает набор файлов в единый комплект документации, пригодный для передачи, согласования и использования.

**Единое хранилище и навигация:**
Все артефакты хранятся в одном месте — Confluence, SharePoint, Notion, корпоративная wiki. Структура должна быть интуитивной.

> **Правило: новый член команды находит любой документ не более чем за минуту.**

- **Древовидная структура** — Проект → Раздел → Документ. Глубина — не более 3–4 уровней.
- **Домашняя страница** — оглавление со ссылками на все документы — карта документации.

**Разделение по назначению и аудитории:**
Разные документы читают разные люди. Нельзя смешивать всё в одном: заказчику не нужны технические детали, разработчику — бизнес-обоснование.

| Аудитория        | Документы                                        |
|------------------|--------------------------------------------------|
| **Бизнес**       | Vision, отчёт об обследовании                    |
| **Разработка**   | SRS, API-спецификации, модели данных и процессов |
| **Тестирование** | Acceptance Criteria, сценарии тестирования       |
| **Поддержка**    | Руководство пользователя, база знаний            |

> **Правило: каждый читатель получает документ, в котором есть всё нужное и нет ничего лишнего.**

**Связность и трассируемость:**
Артефакты не должны быть изолированными островами — они должны ссылаться друг на друга через перекрёстные ссылки, матрицы трассировки и общие идентификаторы.

**Связность позволяет:**
- При изменении найти все связанные артефакты.
- Проверить полноту покрытия требований тестами.
- Восстановить логику решений через полгода.

> **Правило: ни один артефакт не должен «висеть в воздухе».**

**Единый стиль и шаблоны:**

| Что унифицируем                    | Почему это важно                        |
|------------------------------------|-----------------------------------------|
| Шрифты, заголовки, нумерация       | Снижается когнитивная нагрузка          |
| Цветовые акценты и оформление      | Новые члены команды быстрее осваиваются |
| Правила именования файлов          | Проще автоматизировать генерацию        |
| Шаблоны для каждого типа документа | —                                       |

**Актуальность и версионность:**
Документация должна отражать текущее состояние требований — не то, что обсуждали месяц назад.

> **Устаревшие документы опаснее, чем отсутствие документов. Они вводят команду в заблуждение.**

**Инструменты управления версиями:** Confluence, Git для диаграмм в текстовом формате (PlantUML).

**Обязательные атрибуты документа:**
1. Дата изменения.
2. Автор изменений.
3. Версия.
4. Статус: черновик / на согласовании / утверждён / устарел.

### 10.14. Упаковка: форматы представления артефактов

| Формат                  | Инструменты          | Для чего                                                            |
|-------------------------|----------------------|---------------------------------------------------------------------|
| **Текстовые документы** | Confluence, Notion   | Требования, протоколы, отчёты. Живой документ с историей изменений  |
| **Таблицы**             | Excel, Google Sheets | Реестры, матрицы трассировки, CRUD-матрицы. Фильтрация и сортировка |
| **Диаграммы**           | draw.io, PlantUML    | Схемы процессов, модели данных, диаграммы состояний                 |
| **Презентации**         | PowerPoint           | Защита решений перед стейкхолдерами                                 |
| **API-спецификации**    | Swagger, OpenAPI     | Контракты с генерацией кода и тестов                                |
| **Трекер задач**        | Jira, Trello         | Бэклог и User Stories. Прямая связь с кодом                         |

### 10.15. Типовая структура комплекта документации

| Раздел                   | Содержание                                         |
|--------------------------|----------------------------------------------------|
| **Введение**             | Видение, реестр стейкхолдеров, границы системы     |
| **Результаты опроса**    | Модели As-Is, протоколы встреч                     |
| **Требования**           | Бэклог, SRS, варианты использования                |
| **Модели**               | Модель данных, To-Be процессы, диаграммы состояний |
| **Спецификации дизайна** | API, маппинг данных, UI логика                     |
| **Поддержка**            | Руководство пользователя, админ-гид, глоссарий     |

**Как адаптировать под масштаб:**
- **Малый проект** — разделы объединяются. Документация компактная, но структурированная.
- **Средний проект** — типовая структура из 6 разделов — оптимальный баланс.
- **Крупный проект** — разделы детализируются, добавляются подразделы и отдельные томá.

### 10.16. Чеклист готовности к передаче

- [ ] **Версии и статусы** — все документы имеют актуальную версию и статус.
- [ ] **Ссылки работают** — все пункты «да»?
- [ ] **Требования полные** — источник, приоритет и критерии приёмки заполнены.
- [ ] **Нет противоречий** — модели соответствуют текстовым описаниям.
- [ ] **Review пройден** — комплект проверен командой. Структура понятна новому читателю.

> **Все пункты «да»? Документация готова к передаче заказчику или команде разработки.**

### 10.17. Подготовка к согласованию: как защищать артефакты

Согласование — это не «подпишите документ». Это коммуникация с заказчиком и командой, диалог, а не защита диссертации.

**Ключевые артефакты для защиты:**
- Презентация решений — для руководства.
- SRS — для подписания с заказчиком.
- API-контракт — для согласования с командой разработки.

**Принципы защиты:**
- **Связь с бизнес-целями** — каждое требование обосновано бизнес-ценностью.
- **Проработка сценариев** — альтернативные и исключительные потоки предусмотрены.
- **Язык аудитории** — с бизнесом про деньги и риски, с разработкой про архитектуру.

> **Результат: подписанный документ с зафиксированной версией — утверждённый baseline.**

### 10.18. Итоги по упаковке документации

1. **Единое хранилище** — один источник правды, понятная навигация, оглавление как карта.
2. **Разделение по аудитории** — каждый читатель получает только то, что ему нужно.
3. **Связность** — артефакты ссылаются друг на друга через трассировку и идентификаторы.
4. **Единый стиль** — шаблоны снижают когнитивную нагрузку.
5. **Актуальность** — версия, статус, автор — обязательные атрибуты каждого документа.

> **Хорошо упакованная документация экономит часы команды и снижает риски недопонимания между аналитиком, разработчиком и заказчиком.**

## 11. Проверка требований и гипотез: SQL, NoSQL, CRUD, трассировка

### 11.1. Зачем аналитику знать SQL

Аналитик работает с данными — и именно язык запросов является его главным инструментом. Без него аналитик вынужден полностью зависеть от разработчиков в любых вопросах, касающихся данных.

- **Проверка гипотез** — на реальных данных, а не на предположениях.
- **Качество данных** — находить проблемы и аномалии самостоятельно.
- **Обоснование требований** — цифры вместо слов.

> **80% задач покрываются базовыми операциями: SELECT, WHERE, ORDER BY, GROUP BY / HAVING, JOIN.**

### 11.2. SELECT и FROM: основа запроса

| Синтаксис                             | Описание                          |
|---------------------------------------|-----------------------------------|
| `SELECT * FROM "TABLE"`               | Все столбцы таблицы               |
| `SELECT DISTINCT city FROM customers` | Убирает дубликаты                 |
| `SELECT name, email FROM table`       | Только нужные столбцы             |
| `FROM customers c`                    | Короткий псевдоним для читаемости |

> **Результат SELECT — всегда таблица, даже если в ней одна строка и один столбец.**

### 11.3. WHERE: фильтрация данных

| Оператор                       | Пример                                                   |
|--------------------------------|----------------------------------------------------------|
| **Сравнение** `= <> > < >= <=` | `WHERE status = 'Активен'`                               |
| **BETWEEN**                    | `WHERE price BETWEEN 100 AND 500`                        |
| **IN**                         | `WHERE status IN ('Новый', 'Оплачен')`                   |
| **LIKE**                       | `WHERE email LIKE '%@gmail.com'`                         |
| **IS NULL**                    | `WHERE delivery_date IS NULL`                            |
| **AND / OR / NOT**             | `WHERE status = 'Активен' AND created_at > '2024-01-01'` |

### 11.4. ORDER BY и LIMIT

- `ORDER BY col DESC / ASC` — сортировка по одному или нескольким столбцам.
- `LIMIT 10 OFFSET 20` — 10 строк начиная с 21-й — постраничная навигация.

> **Порядок выполнения: WHERE → ORDER BY → LIMIT.**

### 11.5. Агрегатные функции

| Функция     | Что считает      | Пример                                                      |
|-------------|------------------|-------------------------------------------------------------|
| **COUNT**   | Количество строк | `COUNT(*)` — все строки, `COUNT(DISTINCT col)` — уникальные |
| **SUM**     | Сумма            | `SUM(total)` — общая выручка                                |
| **AVG**     | Среднее          | `AVG(total)` — средний чек                                  |
| **MIN/MAX** | Диапазон         | Первый заказ, самая крупная покупка                         |

> **Агрегатные функции игнорируют NULL — кроме COUNT(*).**

### 11.6. GROUP BY: группировка данных

**Шаблон:** `SELECT [столбец], [функция] FROM [таблица] GROUP BY [столбец]`

- Количество заказов по статусам: `GROUP BY status`.
- Сумма покупок клиента: `GROUP BY customer_id`.
- Группировка по нескольким столбцам: `GROUP BY city, status`.

> **Все столбцы в SELECT без агрегатной функции обязаны быть в GROUP BY.**

### 11.7. HAVING: фильтрация групп

- **WHERE** — фильтрует строки **ДО** группировки.
- **GROUP BY** — создаёт группы.
- **HAVING** — фильтрует группы **ПОСЛЕ** группировки.

| Пример                    | Запрос                      |
|---------------------------|-----------------------------|
| Клиенты с суммой > 50 000 | `HAVING SUM(total) > 50000` |
| Статусы с > 10 заказов    | `HAVING COUNT(*) > 10`      |

> **В HAVING можно использовать агрегатные функции — в WHERE нельзя.**

### 11.8. JOIN: соединение таблиц

| Тип            | Описание                                          |
|----------------|---------------------------------------------------|
| **INNER JOIN** | Только совпадающие строки в обеих таблицах        |
| **LEFT JOIN**  | Все строки левой таблицы, NULL где нет совпадения |
| **FULL JOIN**  | Все строки из обеих таблиц                        |

**Пример:** `FROM customers c JOIN orders o ON c.id = o.customer_id`

### 11.9. Подзапросы и CTE

| Инструмент            | Описание                                                       | Пример                                                                  |
|-----------------------|----------------------------------------------------------------|-------------------------------------------------------------------------|
| **Подзапрос в WHERE** | Заказы клиентов из Москвы                                      | `WHERE customer_id IN (SELECT id FROM customers WHERE city = 'Москва')` |
| **Подзапрос в FROM**  | Результат подзапроса используется как временная таблица        | —                                                                       |
| **CTE (WITH ... AS)** | Делает сложную логику читаемой. Можно использовать многократно | —                                                                       |

### 11.10. Типичные задачи аналитика на SQL

| Задача              | Пример                                                                                   |
|---------------------|------------------------------------------------------------------------------------------|
| **Качество данных** | Дубликаты: `GROUP BY email HAVING COUNT(*) > 1`. Пропуски: `WHERE delivery_date IS NULL` |
| **Статистика**      | Объёмы, распределение по статусам, доля каждой группы в процентах                        |
| **Аномалии**        | Заказы с суммой выше `AVG + 3 * STDDEV` — выброс                                         |
| **Сравнение групп** | Средний чек клиентов с email и без — через CASE WHEN                                     |

### 11.11. SQL и NoSQL: две парадигмы работы с данными

| SQL — реляционные БД                                                        | NoSQL — нереляционные БД                                                                        |
|-----------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| Данные в таблицах со строгой схемой                                         | Документы, ключ-значение, графы, колонки                                                        |
| Связи через внешние ключи                                                   | Гибкая или отсутствующая схема                                                                  |
| Стандартизированный язык                                                    | Синтаксис зависит от СУБД                                                                       |
| Когда использовать: структурированные данные, транзакции, аналитика, отчёты | Когда использовать: слабоструктурированные данные, высокая скорость записи, вложенные документы |

> **Аналитик должен понимать обе парадигмы, чтобы работать с любым типом хранилища.**

### 11.12. Проверка требований с помощью SQL

Каждое функциональное требование, касающееся данных, можно и нужно проверить SQL-запросом. Если запрос возвращает строки — требование нарушено. Ноль строк — требование выполняется.

**Примеры:**
- **Уникальность email:** `SELECT email, COUNT(*) FROM customers GROUP BY email HAVING COUNT(*) > 1`
- **Статус без даты доставки:** `SELECT * FROM orders WHERE status = 'Доставлен' AND delivery_date IS NULL`
- **Сумма заказа = сумма позиций:** Сравниваем `order.total` с `SUM(price * quantity)` по позициям заказа.

### 11.13. Проверка гипотез с помощью SQL

Гипотеза — это предположение, которое можно подтвердить или опровергнуть данными. Результат проверки — не просто «да» или «нет», а конкретные цифры для требований.

**Примеры:**
- Клиенты с email совершают повторные покупки чаще — сравниваем среднее количество заказов для двух групп.
- Большинство заказов — в будние дни с 9 до 12 — группировка по дню недели и часу.
- Товары со скидкой продаются в 3 раза чаще — сравниваем средние продажи двух групп.

### 11.14. Аналитические функции SQL

| Функция                                    | Назначение                                |
|--------------------------------------------|-------------------------------------------|
| **Агрегатные** (COUNT, SUM, AVG, MIN, MAX) | Сводная статистика по выборке             |
| **Оконные** (ROW_NUMBER, RANK, LAG, LEAD)  | Анализ последовательностей и ранжирование |
| **Поиск аномалий** (`AVG + 3 * STDDEV`)    | Заказы с аномально высокой суммой         |
| **JOIN и подзапросы**                      | Связываем данные из разных таблиц         |

### 11.15. NoSQL: особенности проверки требований

**Специфика NoSQL:**
- Нет привычных JOIN — данные денормализованы.
- Схема может различаться для разных документов.
- Синтаксис запросов зависит от конкретной СУБД.

**Типовые задачи:**
- Проверка структуры документов — все ли обязательные поля присутствуют.
- Валидация вложенных массивов.
- Агрегация по вложенным полям.

**Примеры MongoDB:**
- Заказы в статусе «Доставлен» без даты: `db.orders.find({ "status": "Доставлен", "delivery_date": null })`
- Количество заказов по каждому товару: `db.orders.aggregate([ { $unwind: "$items" }, { $group: { _id: "$items.product_id", count: { $sum: 1 } } } ])`

### 11.16. SQL для нефункциональных требований

SQL помогает обосновать нефункциональные требования конкретными цифрами: объёмы данных, пиковые нагрузки, темпы роста.

| Задача                     | Запрос                                                            |
|----------------------------|-------------------------------------------------------------------|
| **Объём данных**           | `SELECT COUNT(*) FROM orders` — текущий размер таблицы            |
| **Прирост за месяц**       | `WHERE created_at > NOW() - INTERVAL '1 month'`                   |
| **Пиковые нагрузки**       | `DATE_TRUNC('hour', created_at) + GROUP BY + ORDER BY COUNT DESC` |
| **Кандидаты на архивацию** | `WHERE created_at < NOW() - INTERVAL '3 years'`                   |

> **На основе этих цифр формулируются требования: «Система должна выдерживать N запросов в час».**

### 11.17. Практический цикл проверки требований

1. **Сформулировать** — что проверяем.
2. **Найти таблицы** — где лежат данные.
3. **Написать запрос** — перевести требование в проверку.
4. **Запустить на копии** — никогда на продуктиве.
5. **Анализировать** — интерпретировать результат.

> **Выполняйте запросы только на копии или реплике — никогда на продуктиве. Результаты оформляйте в виде таблиц или графиков для обсуждения с командой и заказчиком.**

### 11.18. Типичные ошибки

1. **Запрос на продуктиве** — может нагрузить работающую систему.
2. **Неточная гипотеза** — «Пользователи активны» — что значит активны? Нужен измеримый критерий.
3. **Игнорирование NULL** — неучтённые пустые значения искажают агрегацию.
4. **Сложный запрос без проверки шагов** — разбивайте на части.

### 11.19. Итоги по проверке требований

- **2 парадигмы** — SQL и NoSQL — обе нужны аналитику.
- **6 шагов цикла** — гипотеза → запрос → результат → вывод → требование → документация.
- **0 строк = норма** — ноль строк в запросе означает, что требование выполняется.

> **Навык написания запросов — один из ключевых hard skills системного аналитика. Он отличает аналитика, который думает данными, от аналитика, который просто записывает слова.**

| **Объём**                    | Сколько шагов/экранов, сколько тестирования, нужен ли ревью                        |
| **Неопределённость и риски** | Зависимость от других команд, непроверенные предположения, стабильность требований |

### Приложение З. Уровни требований

| Уровень                     | Пример                                  |
|-----------------------------|-----------------------------------------|
| **Бизнес-требование**       | Увеличить повторные продажи             |
| **Требование стейкхолдера** | Клиент видит историю заказов            |
| **Системное требование**    | Система отображает заказы за 12 месяцев |

### Приложение И. Пять типов проблем в требованиях

| Тип                 | Описание                                                     |
|---------------------|--------------------------------------------------------------|
| **Противоречия**    | Два требования, которые не могут быть выполнены одновременно |
| **Пробелы**         | Отсутствие информации, необходимой для реализации            |
| **Неоднозначности** | Формулировка, которую можно понять несколькими способами     |
| **Дублирование**    | Одно требование описано в двух местах разными словами        |
| **Избыточность**    | Требования без ценности или не относящиеся к проекту         |

### Приложение К. Принципы структурирования и декомпозиции

| Принцип                   | Описание                                                       |
|---------------------------|----------------------------------------------------------------|
| **Single Responsibility** | Одна причина для изменения — одна бизнес-функция               |
| **Interface Segregation** | Маленькие специализированные интерфейсы вместо одного большого |
| **Data Ownership**        | Каждый компонент владеет своими данными                        |
| **Low Coupling**          | Слабая связанность между компонентами                          |
| **High Cohesion**         | Высокая связность внутри компонента                            |
| **Ортогональность**       | Изменение в одном компоненте не требует изменений в другом     |
| **Abstraction**           | Сокрытие сложности за простым интерфейсом                      |

### Приложение Л. Подходы к структурированию системы

| Подход                      | Плюс                           | Минус                          | Когда применять                       |
|-----------------------------|--------------------------------|--------------------------------|---------------------------------------|
| **По бизнес-процессам**     | Интуитивно понятно заказчику   | Возможны пересечения           | Когда бизнес-процессы чётко разделены |
| **По доменам (DDD)**        | Хорошо ложится на микросервисы | Требует глубокого понимания    | Для сложных систем с богатой логикой  |
| **По ролям пользователей**  | Простота для каждой роли       | Дублирование бизнес-логики     | Для порталов с разными ролями         |
| **По функциональным слоям** | Знакома разработчикам          | Изменение затрагивает все слои | Для монолитных систем                 |

### Приложение М. Типы границ системы

| Тип границы                      | Что определяет                                                 |
|----------------------------------|----------------------------------------------------------------|
| **Функциональные**               | Что система делает, а что остаётся ручным процессом            |
| **Пользовательские**             | Кто с системой работает, какие роли охвачены                   |
| **Интеграционные**               | С какими внешними системами взаимодействуем                    |
| **Данные**                       | Какие данные хранятся в системе, какие — во внешних источниках |
| **Географические и юридические** | Где система работает, под какие законы попадает                |

### Приложение Н. Уровни структуры системы

| Уровень                 | Описание                                              | Аналогия       |
|-------------------------|-------------------------------------------------------|----------------|
| **Система**             | Верхний уровень — продукт или решение целиком         | Жилой комплекс |
| **Подсистема**          | Крупная часть, решающая самостоятельную бизнес-задачу | Дом            |
| **Модуль**              | Логически завершённый набор функций внутри подсистемы | Квартира       |
| **Функциональный блок** | Атомарная функция — одно действие или правило         | Комната        |
